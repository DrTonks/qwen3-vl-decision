# 金融客服任务契约与训练数据审计

2026-10-03。边界续训结束后的下一步审计。目标是把决策任务、训练标签和真正可执行的后端能力对齐，再决定新训练；本轮没有新训练、模型/API调用、数据库访问、部署或Git提交。

## 结论

当前应先整理任务契约，不能仅靠增加轮次弥补。发现三类具体问题：当前Node模型接口仍是旧四路由协议，不能直接接入金融八动作模型；原训练池93.19%使用未来知识库能力设定，当前无知识库场景仅6.81%；部分人工请求与能力说明的标签边界需要明确。

这三点影响业务适配，但**不能据此断言它们造成了上一轮同开发集的回退**。上一轮差异只有少量样本、单个随机种子，详见[结果报告43](43-边界续训结果与离线收尾核验.md)。没有证据证明继续延长训练必然改善，也没有证据证明0.8B容量不足。

## 本轮覆盖范围和证据

- 全量机器盘点11,899条原训练记录与336条边界训练记录，共12,235条；仅直接读取训练文件，没有打开开发/校准/最终题目或预测来构造新数据。
- 独立标签agent针对27条完整输入进行重点阅读，同时全量扫描重复输入与标签；**不是12,235条逐条语义复审**。审核为AI审核，未标成人审。
- 独立代码agent沿Node启动链核对工具能力，用假ORM验证字段、归属、前50项与参数拒绝；没有连接真实数据库或外部模型。仓库声明启动链得到核对，不代表确认了外部服务器当前部署。
- 三项CPU测试覆盖非训练分区拒绝、完整输入冲突检测及审核线索不改标签。来源和输出哈希由独立审计清单校验。

证据：[盘点](../data/financial-contract-audit-v1/inventory.json)、[待复核队列](../data/financial-contract-audit-v1/review-queue.json)、[来源清单](../data/financial-contract-audit-v1/manifest.json)、[独立标签审阅](evidence/financial-contract-audit-v1-labels.json)、[后端审计](evidence/financial-contract-audit-v1-backend.json)。

全量没有“完整可见输入相同而目标不同”的硬冲突。这个检查不能发现语义近似句的规则矛盾，也不证明每个标签正确。

336条补充占合并训练池2.75%，其中52.38%是human；这是一组受控边界对照，不能视为336个独立自然场景。三类固定前缀各出现32次，“这里只允许读取已有内容，不授权新增、删除或改动任何记录。”出现48次。固定表述可能成为分类捷径，但本次只发现风险，未证明模型已依赖这些词。

原训练池不是没有金融数据，而是大多数样本面向“知识库已准备”的未来能力；计划做检索时这些数据仍有价值。下一版应明确区分当前服务、未来检索与登录前鲁棒性，不必强行删掉未来场景或把八类凑成同样数量。当前Node客服入口先鉴权，未认证样本主要属于组件鲁棒性覆盖，不能与真实入口分布混称。

## 真正的后端能力

仓库的`后端/package.json`、`scripts/start-support.js`与`server.js`启动Node链，App请求`/agent/chat`，进入`services/customerSupport`。仓库里的Java工具代码不能证明这条链具有同样字段。

当前`modelDecision.js`使用`support-classifier-v1`，请求`intent/route/tool`三个任务，route为`tool/clarify/llm/human`，其中llm映射answer。执行契约只接受`tool/clarify/answer/human/refuse/close`六动作，缺少`retrieve/redirect`。因此金融八动作训练完成也不能直接换上去；需要另一个明确版本的provider适配器和执行契约。

|工具|当前Node能提供什么|不能据此回答什么|
|---|---|---|
|queryLoanProducts|上架产品编号、名称、金额上限、参考分、标签，最多50项|实时利率、合同条款、个人获批额度|
|queryMyApplications|本人最近50笔的申请编号、产品ID、金额、状态及状态文案|产品名、申请时间、任意历史记录不存在的结论|
|queryApplicationDetail|本人指定编号的产品名、金额、期数、状态、用途|拒贷原因、审批理由、合同条款、还款计划|
|queryMyCreditScore|已有评分、档位、可为空的建议额度|重新评分、正式授信/审批承诺|
|explainApplicationStatus|0/1/2静态状态含义|本人当前实时审批进度|

所有工具须后端鉴权；个人申请和信用数据另外校验账户归属。列表可在**已返回的匹配记录**中回答状态/金额，但最多50项且没有分页参数；列表没有某记录不能证明该申请不存在。新契约建议在单笔编号明确且明细工具可用时优先明细，这不是当前所有provider都已强制执行的统一规则。产品ID不等于产品名，不能把另一个实现的字段补进结果。

**更正此前审核依据：** 文档42引用的边界审核中，部分可替代性讨论参照了Java列表的productName/applyTime。当前Node列表没有这两个字段。本次保留已隔离36条及旧审计原文，不重新放行，也不把“查询提交时间→human”判成已证实的错标；后续重审须用本报告的实际Node能力。

后端输入当前也没有完整的结构化能力档案、带完整性标记的工具结果和失败次数。`handoffAvailable/retrievalAvailable`均为false，不能将human/retrieve决策解释为真实工单或检索已经执行。前置安全guard可能把正常引用风险内容提前拦截，模型根本未被调用；这类问题应在端到端测试单独归因，不能算成模型分类错误。

## 优先澄清哪些标签

启发式队列共184条；53条命中“出现人工/真人但非human/refuse”，139条命中“人工渠道、联系方式、预约/转发”，二者有重叠。它们是**待复核线索，不是184条错标**，不包含自动生成的新金标。

以下例子均来自训练分区。表格只摘录消息，实际复核必须一起看队列或证据JSON中的历史、状态、能力与可用工具。

|训练记录ID|消息摘录|原标签|需要明确的边界|
|---|---|---|---|
|FIN-R4-crosswoz-train-11894-8|你能替我把这段贷款咨询发给人工客服吗？|answer|询问发送能力还是请求人工实际处理；历史也影响含义|
|FIN-R4-crosswoz-train-11396-12|替我预约一次优享贷人工咨询，预约成功后给我编号。|answer|实际个人服务不可执行时，能力说明还是human|
|FIN-R4-crosswoz-train-11095-8|那你们贷款费用的人工咨询渠道给我一下吧。|retrieve|公共联系方式查询与请求转接的区分|
|FIN-R4-crosswoz-train-6046-8|工薪贷的问题我想直接咨询人工，可以帮我找人工渠道吗？|human|明确人工处理诉求与公共资料查询的区分|
|FIN-R4-crosswoz-train-8902-6|那先看看你们的人工咨询方式吧，我想自己联系。|retrieve|仅查官方信息是否具备知识库能力|
|FIN-R4-crosswoz-train-7589-6|不用保证审批通过，给我正规人工咨询渠道就好。|human|只要联系渠道时是否仍应human，需要读上下文|

建议规范已保存到[新契约草案](../configs/financial-support-contract-draft-v2.json)，目前`training_enabled=false`，不是生效中的提示词或后端协议：

1. 明确要求真人处理当前问题→human；人工通道不可用也要如实反馈，不假称已受理。
2. 只查询公开联系方式→有已知可信资料时answer，有正式知识集合时retrieve，否则answer说明限制。不能仅凭“人工”二字分流。
3. 合法但工具办不了的个人业务操作→human；只询问能力→answer；要求越权/造假才refuse。
4. 支持的本人查询缺认证→clarify；能力根本不存在时，不要让用户登录后仍无法办理。
5. 违规要求、引用风险、报告求助应按实际诉求区分；拒绝的是禁止操作，不是含风险词的所有句子。
6. 将人工渠道可用性与会话已经转接的状态分开；当前含糊的`handoff_connected`不能同时承担两者。

这些是待审核的新版本规则，不能追溯替换旧实验的提示词/标签来抬高旧成绩。

## 下一阶段的明确目标与顺序

目标：交付一套**与Node能力一致、语义边界可解释、可版本化复现**的金融八动作数据与接入契约，然后才开启有限预算的新实验。

|顺序|交付物|完成条件|
|---|---|---|
|1，已完成本轮草案|工具字段表、动作边界、184条审核队列|绑定原来源，只读旧数据；当前与未来能力分开|
|2，数据修订|新目录中的逐条保留/修订/隔离账本；自然表述的状态对照组|保留原文和旧标签，所有改变有理由及独立复核；不是关键词批量改标签|
|3，工程契约|新版本八动作provider、能力状态及结果完整性输入；独立端口集成测试|模型输出、guard、参数校验与最终执行分别可观测；不修改默认部署|
|4，新实验冻结|兼容新政策的独立分组评估、训练协议、旧能力回归集|不用旧评测错题造训练；不混用不同政策分数；确认数据/代码/预算后再训练|

训练设计建议先用官方0.8B权重新建LoRA作为干净起点，再按预算决定是否与现有适配器续训对照；这只是设计建议，未启动。首轮从全量覆盖和固定检查点开始，达不到预设要求就结束预算，不靠不断延长观察来挑好结果。新数据规模以场景与状态覆盖为准，不先承诺“更多一定更好”。

新政策/提示词/选项/输入改变后，现有Jev缓存仍可保存为旧实验参考，但不能作为完全同条件的新基线。本轮没有追加API预算；将来若要新的公平对比，应先固定协议、一次性授权成本，再缓存请求。

评估需要分开报告：①模型动作和工具选择；②后端guard/参数落地修改；③真实执行结果。旧八动作冻结集保持原样，只在兼容旧协议的场景用于原口径评估；新政策的独立评估不能简单改旧题标签。过拟合仍需未参与数据构造和选点的新场景组检验。

## 如何查看和复核

先读本报告和新契约草案，再看`review-queue.json`。每条有id、source_file、source_row_sha256、完整input、original_annotation、flags；`decision`目前是待语义复核，`training_eligible=false`。不要直接修改这个已绑定哈希的审计快照；复制到新的修订工作目录，追加建议动作、理由、处理状态和审核人类型，后续经独立复核再发布。用户不必参与才能继续，AI起草/AI复核来源仍需如实保留。

项目根目录执行以下只读验证，无模型加载或API：

```powershell
. .\scripts\use-env.ps1
.\.venv\Scripts\python.exe -m qwenlab.financial_contract_audit validate
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_financial_contract_audit.py
```

`build`仅用于输出目录不存在时重建，不覆盖旧审计。私人PyTorch笔记补充了“标签噪声、任务契约变化与分布变化”的区别；这些分析不意味着已证明某一种机制导致本轮退步。
