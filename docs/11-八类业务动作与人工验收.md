# 八类业务动作：建议保留，先明确边界再独立验收

这是用户提出的下一版客服动作设计草案，**未改动正在运行的第五轮训练**。截图中的八项是 clarify/retrieve/tool/answer/human/redirect/refuse/close，与第五轮探索的“三种非工具路由＋五个具体工具”不是同一套标签。

八个候选可以用 A～H 八个单 token 表示，不需要模型生成八段内容。候选数量本身不是优先精简理由；主要成本仍是模型前向和提示长度。实际困难是类别重叠、缺少可信状态和标注不一致。不能未经实测就承诺八类比四类一样准、一样快。

## 动作边界与反例

|动作|建议定义|重要反例/必要状态|
|---|---|---|
|clarify|缺少完成当前步骤的必要信息，补问或确认|缺申请编号、模糊指代；不是一遇低置信就无限追问。需要看到当前待填字段。|
|retrieve|需要当前有效的业务规则、合同说明或产品知识，现有证据不充分|问“提前还款有什么规定”，尚无有效文档时检索；过期、错产品或错地区的材料不能算已有证据。|
|tool|需要实时或个人业务数据，现有事实不充分|查审批进度、本人信用分。仍需具体工具名、参数与后端鉴权；缺字段先clarify。|
|answer|已有足够且有效的依据可回答，或只需普通问候/解释|刚查到当前申请状态；不能因大模型似乎知道贷款规则就跳过需要的检索。回答形式可模板或回复模型。|
|human|明确人工诉求、账户安全/争议，或流程确实需要人工且无法自动完成|重复扣款、疑似冒用。工具首次可重试错误不必一律转人工；没有真实转接能力时不能伪造“已受理”。|
|redirect|当前内容在服务范围外，用简短回复引导回客服主题|旅游攻略与贷款问题无关；若“旅游贷款用途是否允许”，仍是业务问题。|
|refuse|用户要求执行明确不允许的操作，拒绝该具体操作|“把拒绝改成通过”不能交人工暗示可代办；“为什么拒绝、如何正式申诉”不是非法操作，应查详情/检索/转人工。|
|close|用户明确结束且当前流程没有必须继续处理的事项|“谢谢，但还有一笔没查”不能关闭；“好的”可能只是确认编号。终止的是本次咨询，允许新发起。|

权限检查独立于动作分类。无论模型选什么，后端都不能执行越权操作。存在多个诉求时需要记录主动作和待办事项；不能用一个标签假装解决所有问题。拒绝违规操作与安排合法申诉可同一回复体现，不能为了单标签抹去后者。安全风险仍需人工跟进时，应保留案件状态，不让一句“谢谢”关闭未完成处理。

## 是否精简

建议业务协议保留八项，再测“八类平铺”与“六类模型＋流程规则”两种实现。后者可把显式结束事件与服务范围判断交给独立流程/策略；八项业务语义仍存在。不要仅为了类别少把 retrieve/answer 合并，那会失去“是否必须先找依据”的决策；也不建议把 refuse/human 合并，二者对权限和用户预期的含义不同。

close 最适合首先用流程状态约束；点击明确的结束按钮可由代码处理，自由文本的结束语则要结合上下文。redirect 也不能只靠关键词规则，边界模糊时仍交给模型判断。六类不一定更快更准，额外规则或分类器也有成本，需同一人工验收集对照。

## 每条输入是否都调用模型

每条用户事件都应经过客服流程控制，但不必每次都做完整的大模型动作分类：

1. 人工已接管：按会话归属送人工，不重复争抢路由。
2. 正在等待明确字段/按钮：校验输入是否符合该字段，如确认编号；合法且没有新诉求时直接推进。出现改口、插入安全投诉或新问题则回到动作决策。
3. 可信系统事件：只读工具成功返回、参数错误、超时次数等，能按固定流程处理的由代码处理。含糊或多步情况再让模型判断。
4. 新自由文本、意图切换或上下文不明确：调用动作模型。

明确的结束按钮、可验证字段提交、同一请求ID的重试等可由代码完成；不要把孤立的“好”“谢谢”匹配成结束。缓存必须包含用户、会话、可信状态版本等约束，不能复用别人的个人业务结果。当前这是集成建议，实验仓库尚未实现真实客服状态机。

tool 分支仍要选具体工具。可以用单独的工具分类，也可以已有意图/字段能够唯一确定时按代码映射；候选很多或有歧义时不能硬映射。参数校验与真实执行由应用完成，模型输出本身不执行工具；这也符合 [Transformers 工具调用文档](https://huggingface.co/docs/transformers/chat_extras)区分模型请求与应用执行的流程。

## 人工验收集：需要，且不能直接改旧标签

第五轮没有 retrieve/answer/redirect/refuse/close 的专项监督。旧 llm 标签可能分成 retrieve、answer、redirect、close，旧 human 中部分修改审批请求在新协议下属于 refuse。不能机械重命名旧标签，更不能用旧四类路由的98%宣称八类效果。

建议先做 **500条独立验收**：八类各40条作为覆盖起点（320），另180条覆盖边界、多轮和状态对照。同一原始场景的改写与状态对照保持同一组；500行不等于500个独立场景。生产占比另做一份真实流量评估，类别均衡集不代表线上平均成本。

重点成对设计：

- 同一句问规则，分别无依据/有当前有效依据/仅有过期依据：retrieve/answer/retrieve。
- 同一句查申请，分别未登录/已登录但缺编号/参数齐全/已有充分最新结果。
- 问为什么未通过 vs 要求直接改为通过 vs 询问合法申诉。
- “谢谢，解决了” vs “谢谢，但还有问题” vs 安全案件尚在处理中。
- 超时一次可重试 vs 重试失败 vs 权限拒绝。
- 多轮改口、口语省略、引用他人话语、干扰分类指令、多诉求和范围外问题。

两位项目成员分别盲标，不看模型/Jev结果，标出主动作、必要工具、缺失字段、证据充分性、理由和政策版本；分歧先仲裁。冻结哈希后才测试。可以使用助手提供的草稿辅助工作，但应标明来源，不能自称独立人工金标准。公开数据可补通用能力，不能直接提供平台专属八动作标签。

模板在 `data/review/support-actions-v1-template.csv`，只有表头；未伪造500条已完成标注。含真实对话的填写版本应放 `.local/review/` 并先脱敏，不自动上传GitHub。该空模板所在目录需加入发布白名单。

验收指标至少包括八类准确率/宏F1、各类召回率、必须人工漏转、正常请求误拒绝、错误提前结束、需要依据却直接回答、tool子集的“动作＋工具＋参数”联合正确率，以及请求级P50/P95和实际模型调用次数。跨多个轮次还要看流程完成率、重复检索/循环追问，而不是只有单句分类准确率。

先比较原始Qwen、当前第四/第五轮模型和Jev在新协议上的基线。若八类边界仍明显不足，再准备与验收分组隔离的训练/开发/校准集做专项微调；**不能用这500条验收数据训练后再报同一套分数**。
