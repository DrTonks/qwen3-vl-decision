## 从代码确认了什么

实际运行入口是`后端/server.js`注册`后端/api/agent.js`。它使用关键词匹配调用本地查询函数，未匹配时尝试回复模型或回退。不要把`后端/agent/`中的Java参考实现视为当前Node已经具备的能力。

App的`Uni-ui/pages/profile/support.vue`只向`/agent/chat`发送`sessionId`和`message`。当前Node没有按sessionId加载/保存对话历史，没有把页面状态、工具结果结构化传入决策模型。`sessionId`随回复返回，不等于已经实现会话记忆。输入框也没有发送图片，因此本版只做文本；用户说“你看图”时不能假装已接收图像。

|业务能力|当前证据|设计稿如何处理|
|---|---|---|
|产品、本人申请列表、详情、分数、状态码解释|Node有五个本地函数，详情按登录身份和申请ID查询。|可以建议调用现有查询，但八类分发及参数提取协议仍待开发。|
|知识检索|未在当前Node客服链路发现索引、检索接口或版本化业务知识库。|retrieve表示待设计的知识获取步骤，不能宣称现在可执行。|
|人工受理|未发现客服工单或真实转接接口。|human表示需要人工，不能回复“已转接”“已退款”或生成虚假工单号。|
|合同/材料/还款业务|有业务API和App页面。|不是已经开放给客服的工具；查询封装与授权范围另行确定。|
|审批、支付、签约、修改信息|业务代码可能提供写接口；参考客服原则为只读。|客服不替用户执行写操作，不能把普通业务API全部交给模型。|
|设备风险工作台|`/device-risk`需要管理员身份。|普通用户不得通过客服索取他人关联数据或管理端证据。|
|结束咨询、拒绝、范围引导|当前没有独立动作协议；Node还允许非业务闲聊。|这些是新的产品语义，必须由团队确认，不能拿现状回复当金标。|

已有查询函数的精确边界也需要注意：

- `queryLoanProducts`实际返回产品名、最大额度、准入分、上架标志和标签，**没有返回真实产品的利率和期数**，也未在函数中只筛上架项。不能假定它能直接回答所有产品条款问题。
- `queryApplicationDetail(userphone, applicationId)`检查归属，但调用方的数字提取目前使用首个整数；“申请76001，状态2”容易混淆两个数字。测试稿分别写清编号和状态参数。
- `queryMyCreditScore`使用模型评分及profile；普通用户评分接口的fallback字段不同。缺失、0值及口径需要工程侧核对，客服不能自行编造或统一成某个固定分数。
- Node演示产品与数据库种子产品不同，准入分口径也不同。稿件只把种子名用于构造问题，不把演示利率或600分门槛当生产规则，更不承诺达到某分就一定通过。
- 当前`/agent/chat`要求用户登录；访客/登录过期/管理员身份的用例用于前置流程验收，不应真的发送给决策模型。

## 先讨论处理结果，再决定动作名

下表是候选划分，不是已批准接口。

|候选动作|期望处理结果|必须讨论的边界|
|---|---|---|
|clarify|获得尚缺少、且会影响下一步的信息。|登录拦截不需要模型；不要明知已给编号还重复追问。|
|retrieve|从有效业务说明中取得依据。|固定状态映射是否根本不需要检索；没有文档时如何回退。|
|tool|用受限只读查询获得最新业务事实。|工具清单、参数和返回协议尚未统一；一个动作是否允许多个查询。|
|answer|已有足够事实时组织回复，或简单问候。|answer不是“无需回复模型”；不能凭空回答实时事实。页面引导是否也归这里？|
|human|问题需人工权限、核查或明确人工服务。|渠道尚未实现；无法转接时怎么如实回复。|
|redirect|把无关请求引回服务范围。|本App技术故障属于业务范围，不可误拒。是否单独保留此动作？|
|refuse|拒绝明确不允许的操作，同时可提供合法途径。|“没有该工具”不等于恶意请求。普通写操作引导本人操作，是否归answer而非refuse？|
|close|结束当前客服事项，后续仍可重开。|“谢谢”“好了”不总是结束；绝不是取消贷款、销户或删除记录。|

优先级也尚未冻结。可先采用以下**讨论顺序**审查案例，而不是马上硬编码：

1. 先由后端处理身份、角色与工具权限。
2. 确认用户是否在请求越权或篡改；拒绝具体操作与受理合法申诉不能混为一类。
3. 明确安全事件、扣款争议、人工请求是否应升级。
4. 对普通业务，先确定对象与必要信息，再检查已有事实是否足够，最后选择查询、查文档或回答。
5. 识别服务范围与明确结束；不要让礼貌用语压过同条消息中的新业务请求。

## 建议团队优先拍板的六件事

1. **固定状态码映射。** `0未通过 / 1已通过 / 2待审批`已有函数。它是tool、answer，还是完全绕过模型的确定流程？稿中保留tool建议和讨论点，不当作不可变金标。
2. **缺能力时怎么办。** 合同、材料、账单查询有业务API但没有客服封装。需要补只读工具，还是引导用户去页面？部分草稿先用human表达需升级，团队应改成选定的规范。
3. **普通写操作与非法操作。** “帮我还款”可能只是合理操作诉求，不能和“篡改审批结果”同等对待。稿中相关refuse是候选，需要复核是否改成answer并引导本人确认。
4. **human与refuse。** 正常申诉建议human；绕过审批改结果建议refuse并说明申诉途径。不能沿用旧训练数据将所有相关问题都机械归human。
5. **检索的起点。** 页面操作说明可以从现有实现整理；利率口径、提前还款、费用与期限等必须由业务成员确认，不能直接把代码细节或示例当正式条款。
6. **会话结束与重开。** 定义close作用域、是否有未解决事项、短句确认的上下文，避免把“好了，我登录了”当结束。

这六项确定前，可以修改、合并或拆分候选动作。**不要为了凑八类而改变正确的业务处理结果。**

## 输入与输出草案的性质

每条`inputs`包含当前消息、最多两条历史消息、`state`、可用工具列表和空图片列表。状态里的业务数据全部是测试夹具，编号76001/76002、分数612等均不来自真实数据库，也不保证seed运行后有对应记录。

`facts`模拟后端已获得的事实，`ui`模拟App传来的页面状态，`last_tool`模拟工具执行结果，`knowledge`模拟已审核片段。**这些不是现有`/agent/chat`请求字段，也不代表相关能力已经接通。** 将来状态需要服务端验证或明确来源，不能直接信任客户端声称“已登录”“属于本人”或“允许管理员访问”。

涉及“我要申诉”“请求直接扣款”等意图信息写在用户历史消息中，未放置预先标好的`requested_operation`/`intent`来替模型完成任务。仅输入JSONL不携带建议动作、期望步骤或复核结果，避免评估标签泄漏。

候选输出暂放`proposal`，最终人审结果放`review`。当前没有正式`labels`字段，`final_action`为null。未来可以在动作规范冻结后另写转换器，不能直接拿`proposal.action`当训练或评测金标。

## 人工复核怎么做

1. 先读能力清单和待决议项，再看[盲审输入册](../data/support-design-v1/blind-review.md)。先写自然语言的下一步及理由，不强迫选八类。
2. 优先复核120条状态边界和40条短上下文；每组连着看，检查同样问题在不同事实下为何应该改变处理。
3. 再看建议稿，记录接受、修改、待讨论或删除。至少检查：信息够不够、是否需要查询、工具实际能否提供所需字段、是否越权、是否误转人工、能否承诺操作已完成。
4. 建议两名成员独立复核高风险边界，再由一人记录共识。尚有分歧时保留`needs_discussion`，不要为了可评分而强行选唯一答案。
5. 将`review-template.jsonl`复制到`.local/review/`填写，或先在建议稿副本逐条批注；含成员姓名/真实例子的工作稿不直接提交GitHub。公开版本应只保留去标识化后的共识。
6. 动作语义批准、案例标签审定后，再去重并按场景组冻结验收版。未来训练数据应另行构造；这一轮看过、讨论过的案例也不应被宣称为完全盲测。

复核状态建议值：`pending / accepted / revised / needs_discussion / excluded`。建议填写最终动作、工具及参数、期望下一步与理由；如果决定不用八类，`final_action`可以使用新协议中的名称，不能被当前候选表限制。

最终报告应分开给出：登录/角色流程结果、动作准确率与每类召回、真正需要工具时的联合正确及参数正确、人工漏转与误转、非法查询/写操作误放行，以及短上下文变更一致性。先按场景组看错在哪里，再讨论总分。当前不设未经团队确认的上线阈值。
