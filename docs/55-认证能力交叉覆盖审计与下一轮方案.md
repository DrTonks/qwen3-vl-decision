# 认证能力交叉覆盖审计与下一轮方案

2026-10-04。本轮只审计既有13,242条训练候选、上轮冻结曝光清单与真实Node参数解析代码，没有加载模型、训练、请求API、修改旧标签或打开开发/校准/最终题面。结论是：**优先改变登录前场景内部的抽样，而不是立即增加训练总量。现有数据足以做下一轮有限对照。**

## 一个被大分类掩盖的覆盖缺口

|可信认证状态|知识库能力|池内条数|故事组数|普通组曝光|分层组曝光|
|---|---|---:|---:|---:|---:|
|已登录|有|7,108|4,019|1,654|800|
|已登录|无|1,699|396|445|1,920|
|未登录|有|4,091|2,545|1,018|461|
|未登录|无|344|91|83|19|

每组训练总曝光为3,200次。故事组可能跨认证/能力组合，表中各行故事组数不能相加当独立总数。

上轮“登录前鲁棒性”共4,435条，但其中4,091条带未来知识库能力，只有344条没有知识库。冻结政策允许未登录时检索可用的正式知识，而白名单工具都要求认证；不能把未登录但有知识库的retrieve标签全部当作错误或删除。

分层策略给登录前总计480次曝光，却没有在这个大类中继续区分知识库能力。无KB子类从普通组83次降到19次，仅占分层组全部曝光的0.59%；有KB子类占461次。这与组轮转也有关：无KB只有91个故事组，而有KB有2,545组；按组轮转并不自动保持按行比例。这里解释的是实际清单分布，不是已经证实的模型退步因果关系。

无KB登录前的现有覆盖并非空白：

|动作/边界|池内条数|故事组数|普通组曝光|分层组曝光|
|---|---:|---:|---:|---:|
|缺认证，需要clarify|82|41|23|4|
|缺报错上下文，需要clarify|15|3|2|0|
|缺具体诉求，需要clarify|20|4|4|2|

该子类还包含answer90条/40组、human44条/19组、refuse38条/13组、redirect35条/11组、close20条/8组。当前最先能修的是“已有内容未被抽到”，不是把所有动作机械补到同样多。缺报错上下文和缺诉求只有3、4个故事组，若以后单独强化这两类，应补独立故事覆盖，不能靠重复同几组制造数据量。

此外，训练池中有73组精确同消息、同历史、不同可信认证状态的对照，每组包含tool/clarify切换。它们来自既有训练故事，不是本次照开发错题新造的训练题。是否纳入下一轮及曝光多少，需要在新清单冻结时明确记录。

## 工具能力与参数不能只看是否有字段

13,120/13,242条输入列出全部五个工具，部分可用或全部不可用仅122条。该能力变化比默认全工具场景稀疏，应单独统计和保持覆盖；不能仅按工具名总量判断“能力边界已经充足”。本次按认证、知识库、工具全量/部分/空集、动作、参数形态输出了交叉单元，见[覆盖明细](evidence/financial-coverage-audit-v1/coverage-cells.json)。

基本硬约束检查发现0条矛盾：没有未认证标tool、没有选择不在输入白名单的工具、没有选择不可用知识集合的retrieve。这是结构检查，不等于完成了所有语义标签的独立复审。

对全部训练输入调用真实Node的`financialContract.modelInput/toDecision`纯函数，重建可见消息、历史、pending和已选申请编号；不启动后端、数据库或模型。这里输入给toDecision的是标注动作，不是模型预测。

工具标注有215条在此重建上下文中变成clarify：

|输入层与工具|条数|解释|
|---|---:|---|
|当前服务宽契约组件，状态解释|132|原输入有合法state.status_code，但真实Node重新从当前消息/pending解析；重建后未获得有效参数|
|未来能力宽契约组件，申请详情|82|原输入有state.application_id，真实解析器不会无条件沿用旧编号；当前消息与已选编号不足以重新解析|
|未来能力宽契约组件，状态解释|1|同类结构化状态与重建解析差异|

**这215条不能直接标成“错标”或删除。** 宽契约组件允许服务端提供可信结构化参数；本次重建并不是当时真实会话，更不是模型端到端失败。真实Node投影层的训练样本没有发现此类动作变化。保留下来的tool动作，其解析参数与标注参数不一致的数量为0。

当前无KB服务的详情目标包含137条结构化编号和37条需Node从可见输入解析编号；状态解释包含258条结构化状态码和10条需从可见输入解析状态码。不能把“没有state字段”一律算缺参，也不能把“有字段”一律算能在实际Node会话执行。审计脚本把结构化、Node可解析和Node未解析分别记录。

标注missing_slots还存在`applicationId/application_id`与`statusCode/status_code`两种写法。这里只在统计时合并别名，旧文件未改写；这属于数据规范整理问题，不能据此认定动作标签错误。

## 下一轮建议：只替换登录前的480个位置

建议以刚完成的分层400步为历史对照，先准备以下候选清单：

|部分|旧分层曝光|新草案曝光|
|---|---:|---:|
|已登录、无KB、真实Node投影|1,440|1,440，原行和位置保持|
|已登录、无KB、宽契约组件|480|480，原行和位置保持|
|已登录、未来KB|800|800，原行和位置保持|
|未登录、无KB|19|320|
|未登录、有KB|461|160|
|合计|3,200|3,200|

这样保留全部2,720次已登录曝光，仅在旧登录前480个位置内改变能力组合。不要同时改学习率、loss权重、模型起点、训练步数或已有门槛，否则难以解释结果差异。新数据分配仍可能影响已登录表现，不能保证其他能力都不回退。

**CPU容量检查已通过，但尚未生成或冻结清单。** 固定2,720次已登录曝光后，扣除每个故事组已使用次数，在每组最多16次约束下，无KB登录前仍有344条可各取一次；有KB登录前若只用与这91组互不重叠的故事组，还有4,064条可各取一次。因此320＋160在这些约束下可行，不需要重复登录前样本。此证明没有验证细粒度动作配额、顺序、token成本或语义独立性，也不构成训练许可。

接下来的实施顺序：

1. 在新版本目录生成候选采样清单；先保证认证补充、普通追问、拒绝、引导、结束等现有子类不被饿死，再校验全局行/故事组上限和覆盖。不能凭开发错题调整具体行的抽样权重。
2. 比较新旧清单，核实仅480个指定位置变动，已登录行及位置完全一致；补实际token、工具任务数与独立故事组预算。若约束不同时可满足，明确报告，不能静默破坏固定部分。
3. 独立复核新计划与执行器适配，冻结新的实验版本后再决定启动。从官方0.8B与相同初始化重新训练，不能直接在旧400步末端续训来声称只是改变采样。
4. 原开发集只用于持续开发/回归，最终测试仍不得用于选行或训练。需要新的独立评估场景时，从业务规范和新故事组构造并复核，不能复制既有开发错题的近邻。

本轮完成的是审计与容量验证；没有新增训练语料、修改旧训练/评估文件、生成新训练排程、启动训练或更改后端行为。
