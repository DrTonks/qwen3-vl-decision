# 中文客服决策模型：第一轮实测报告

日期：2026-09-26。项目根目录为本仓库。此报告保留第一轮实验口径。

## 本轮结论

本机已经真实跑通 Qwen3-VL-2B-Instruct，并完成 Jev API 对照。当前提示、候选和样本下，未经领域训练的 Qwen 首 token 方案明显落后于 Jev，不能直接替代。

首 token 方案确实比短标签生成快；但生成一个概率分布不等于得到可信概率。温度校准能改善概率质量，不能修正排序错误。另一方面，工具字段的大量错误可以用后端确定性规则消除，应先优化工作流再判断微调收益。

本轮没有微调或蒸馏，也没有把任何预测接到真实贷款工具。关于是否训练或采购 Jev，留待讨论决定。

## 已完成的工作与环境

- 阅读现有 `后端/api/agent.js`，整理5种现有内部工具，建立意图/路由/工具/人工标记契约。
- 编写192条中文业务样本，48个场景组；64开发、56校准、72测试，场景组互斥。
- 下载MASSIVE 1.1官方中文分片，从原始test分区按类别最多抽2条，得到117条、59类。
- 下载Qwen官方ModelScope权重，逐文件验证SHA256，保留文件revision及下载清单。
- 建立D盘独立环境：Python 3.12.5、PyTorch 2.8.0+cu128、Transformers 4.57.1。
- 完成首token、短标签生成、Jev、温度校准、候选顺序扰动以及离线工具门控实验。
- 保存逐条预测、概率、耗时、模型版本、数据哈希、错误明细与可复现命令。

GPU：RTX4060 Laptop 8GB。BF16、batch=1、SDPA、无量化、无CPU卸载。本地测试峰值allocated显存约4.18GiB；这是PyTorch分配统计，不包括驱动和桌面开销。结论只覆盖本轮短文本，不能据此保证长上下文、图片或训练也只占4.18GiB。

环境、模型、缓存均在qwen目录。`scripts/use-env.ps1`把后续安装TEMP/TMP、HF_HOME、TORCH_HOME、PIP_CACHE_DIR全部指向D盘。首次PyTorch安装曾使用系统临时目录，安装后已结束；没有将模型或新Python环境装到C盘。

Jev请求使用`jev-latest`，本次所有实际响应均为`jev-1.13.0`。账号模型发现接口只返回latest/preview别名，因此未来运行不保证仍是相同版本，脚本会记录实际返回版本。

## 数据性质和实验方法

业务样本是助手依据项目政策编写的`synthetic_unreviewed`规则一致性测试，尚未由两名成员复核，不能称为人工黄金集。句式相近，同组4条不独立。首版192条没有达到此前建议的约300开发+500独立验收规模，扩充真实脱敏样本和人工审核仍是下一阶段任务。

测试标签不进入模型输入。模型输入是同一用户表达、对话历史、业务状态、可用工具列表、政策和候选说明。业务任务四个输出为intent、route、tool、needs_human；公开集只评意图，不强行推导贷款工具标签。

MASSIVE中文完整数据有60类，但该版本中文test分区实际只有59类，缺少cooking_query；其中一类只有1条，因此抽样共117条。本次候选范围限定这59类。这是中文意图子任务，不能与60类全量官方榜单直接比较，也不代表贷款中文分布。

本地首token：验证每个候选符号为单token，读取输出位置logits，在候选集合内softmax，同时保存全词表上的候选总概率质量。生成基线：同一提示，贪心生成最多8个token，严格单符号格式；多余文字记为格式错误。

Jev原生choice接口一次输出四个问题；本地逐问题运行四次。信息一致，模型接口和内部计算不同，因此结果是当前适配方案的对照，不是对模型架构的等价证明。未使用few-shot、专用决策头、模型权重训练或提示搜索。

额外64条开发分组也完成对照：Qwen意图70.3%、路由62.5%；Jev意图90.6%、路由89.1%。它们单独报告，不与正式测试混算。56条校准分组仅用于Qwen的概率温度拟合。

对相同案例按场景组bootstrap 2000次，Qwen首token减Jev的业务路由准确率差为-33.3个百分点，95%区间约[-54.2,-13.9]个百分点。公开中文意图差为-16.2个百分点，95%区间约[-23.9,-8.5]个百分点。这支持本轮配置有明显差距，但不能泛化到所有提示、模型规模或微调版本。

## 工具规则为什么必须加入

在真正应调用工具的20条中：Jev选对工具20条，Qwen选对18条；路由和工具同时正确则分别为20条、17条。

原始整体工具准确率偏低的主要原因是跨字段矛盾：路由说“解释/转人工”，工具字段却仍指定查询。Qwen有41/72条路由与工具矛盾，Jev有9/72条。

`apply_route_gate.py`用不读取标签的规则：`route != tool`时将tool设为none。Qwen工具字段准确率由31.9%提升到84.7%，Jev由84.7%提升到97.2%。这些是离线后处理结果，推理耗时沿用原始请求；不为确定性覆盖后的工具字段伪造概率评分。

该规则不能修复路由本身。例如Qwen把“查询别人贷款详情”误判为可调用工具，仍然需要身份归属和工具权限检查。后续可把工具选择限定在route=tool的分支，其他分支由代码直接设none，减少无意义推理与矛盾。

## 概率、格式和顺序稳定性

| 业务测试指标（越低越好） | 原始Qwen | 独立校准后Qwen | Jev |
|---|---:|---:|---:|
| 意图ECE | 0.3715 | 0.1344 | 0.0724 |
| 路由ECE | 0.2682 | 0.1685 | 0.0606 |
| 工具ECE | 0.5188 | 0.1862 | 0.0800 |
| 路由NLL | 2.8215 | 1.3349 | 0.1292 |

温度仅在56条校准组拟合，测试组从不参与拟合；模型权重未改变。预测选项及准确率保持不变。

以路由候选最大概率>=0.9筛选：原始Qwen接受51/72条，其中16条错误；校准后接受22条，其中4条错误；Jev接受53条，本轮0条错误。这个阈值观察是事后探索，样本小且相关，不能直接当成上线阈值或零风险保证。

候选顺序及符号映射随机置换一次后：72条中意图改变10条、路由改变6条、工具改变20条。平均总变差分别约0.142、0.081、0.278。该随机种子没有交换二分类needs_human的两个选项，因此其0变化没有稳定性证明意义。

生成式基线的意图、路由、工具与首token在业务测试中完全一致；needs_human有29条输出了符号后的额外说明，按严格格式计为无效。例：输出`A: 必须转人工 (`。这主要是输出格式问题，不能解读成29次语义选择都不同。公开集两种模式严格答案一致115/117条。

候选总概率质量已保存，可排查是否只是强行将很小概率归一化。本轮业务平均候选总质量接近1，但仍有明显高置信度错判，说明问题不只在归一化。

## 两个需要人工核查的失败案例

1. Jev：用户“反复重登更新都没用，还是无法申请”；状态给出前后端冲突且普通排查失败。标签要求human，Jev给tool且needs_human=no。应检查模型是否充分利用已完成排查状态。
2. Qwen：用户“我不是借款人，查询1003的个人详情”；状态明确记录归属other_user。route给tool，但needs_human=yes，内部判断矛盾。工具后端必须执行归属校验，不能仅信任路由模型。

错误CSV包含全部不一致项，样本ID可回查JSONL中的原文及状态。

## 调用量和估算费用

Jev成功请求257次：4次接口冒烟、72次业务测试、117次公开测试、64次开发补充。未自动重试，无失败请求。
API返回累计400,858 input tokens、102,418 output tokens。按官方公开价格每百万输入$0.042、输出不计费估算约 **$0.01684**。
这不是控制台账单或余额核验；实际扣费以服务方账单为准。规则后处理没有再次调用API。本地成本没有按电费/折旧估价。

## 下一步的选择依据

- 若目标是尽快验证客服链路：当前证据偏向Jev加后端规则、权限检查与人工兜底；它同样不能直接上线自动执行敏感操作。
- 若目标是本地部署与项目研究：保留Qwen路线；先在开发集验证更短提示、路由后再选工具的分阶段流程，再用全新人工审核测试集确认收益，随后再决定是否QLoRA。
- 本次没有证据能保证微调后追平Jev，也没有证据说明小模型路线无法达到要求。当前实验否定的是“原始首token直接平替”在这组任务上的效果。
- 先人工复核192条政策样本，补齐真实中文咨询、所有意图的独立测试覆盖和足够高风险案例。现有72条测试并未覆盖所有意图，部分信用分、扣款争议场景在开发/校准分区。
- 图片阶段另建截图+同一业务状态的配对集，包括灰色按钮、产品下架、实名认证未完成、额度超限。当前runner明确拒绝非空images，不能把图片路径当文本伪装成多模态验证。

模型源码、数据、命令和测试记录都已准备。当前停止在评测阶段，等待下一轮决定微调还是采用Jev。
