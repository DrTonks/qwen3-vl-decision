## 2. 真实后端约束带来的两处修正

**第一，工具缺失不能一律标成转人工。** 初稿计划把所有unavailable版本都设为human。独立审查先隔离了公开目录和状态说明的16个故事。复核冻结策略后，公开目录/静态术语查询在没有工具、没有知识库、没有已有结果时，改为answer如实说明能力限制；个人业务查询仍选human。answer不能编造产品或状态事实，human也不能声称工单或转接已经成功。

后端`toDecision('tool', ...)`会将不可用工具调用挡成human，这是错误调用的保护措施，不是上游语义标签的判定器。本轮分别保存正确动作落地结果与强行选tool时的保护结果。16条公开目录/状态说明的unavailable样本，两层动作不同是已解释的设计事实，不是伪造一致性。

**第二，状态码不能假装存在服务端记忆。** 实际Node支持保存`selectedApplicationId`，当前消息“这笔/那笔”可解析到可信申请编号；但状态码仅从当前消息、必要时结合pending字段解析，没有`selectedStatusCode`。因此：

- 40对认证对照：只改变`state.authenticated`。
- 40对能力对照：只改变`available_tools`中目标工具是否存在。
- 8对申请编号对照：只改变`state.application_id`是否存在。
- 8对状态码缺失补充：改变`message`和`state.status_code`，**不计入纯状态对照**。

合计88对单字段对照、8对文字变化补充。所有历史为空；同组认证、能力及申请编号对照保持当前提问完全相同。当前契约要求全部工具认证，包括公开目录和静态状态工具，本轮没有偷偷放开认证。

## 4. 文件位置与复查方法

收尾脚本补审曾发现“复核变体被放错故事组时，可能隔离错组”的边界缺口。已加入逐组ID集合验证和错组负测，同时核对长度报告的执行脚本及提示编码器SHA。当前136条复核记录本身没有错组；保留了修复前证据，修复后重新收尾、重放，候选内容和接受数量均不变。独立修复确认通过、无剩余阻断，见[补审证据](evidence/financial-state-pair-candidate-readiness-review-v1.json)。

主目录：`data/financial-state-pair-candidates-v1/`。

- `stories.json`：40个原始故事，最适合先看中文提问是否自然、业务是否成立。
- `build/REVIEW.md`：136条完整模型输入、预标注、参数、缺失项及变更字段。
- `build/authoring.json`：离线服务端上下文；`build/candidates.json`：真实适配后的候选。
- `build/grounding.json`：正确动作与强行查询的后端保护结果分列。
- `build/pairs.json`：88+8对的ID和实际变化字段。
- `checks/`：独立复核、盲查、token长度与旧输入回放证据。
- `reviewed-candidates.json`：收尾后可供下一阶段采样设计的候选副本，仍非训练入口。

复查时按**故事整组**看：同一句话切换认证后是否应追问；目标工具缺失时是否属于需要人工的个人业务；详情编号是否来自可信选中对象；状态码是否明确；答案是否要求了工具根本不返回的字段。不要直接编辑build下的生成文件、审核结论或哈希。需要调整时先复制为新版本作者稿，记录理由，再重新投影、复核及隔离；旧版本保留以便追溯。

命令在仓库根目录运行；相邻业务仓库默认名为`uestc_Integrated_Design`，也可显式传入后端目录，不在数据里保存本机绝对路径：

```powershell

.\.venv-qwen35\Scripts\python.exe -m qwenlab.financial_state_pair_candidates verify
.\.venv-qwen35\Scripts\python.exe -m unittest discover -s tests -p test_financial_state_pair_candidates.py
.\.venv-qwen35\Scripts\python.exe -m unittest discover -s tests -p test_state_pair_readiness.py
.\.venv-qwen35\Scripts\python.exe scripts/finalize-state-pair-candidates.py verify
```

首次生成使用`build --output <新目录>`，已存在的目录拒绝覆盖。首次盲查为`scripts/screen-state-pair-candidates.py`，首次长度/旧输入检查为`scripts/check-state-pair-inputs.py`；两者保留不可覆盖的检查文件。日常查看已有证据或运行verify，不反复重建作者稿。Windows临时目录曾出现ACL拒绝访问，现使用D盘`.local/`下正常继承权限的新目录重放，并保留原失败前草稿；这没有改变训练数据策略。

## 5. 接下来如何判断这批数据有没有价值

下一阶段先冻结成对采样方案，再决定短训。以报告58的400步方案为基线，明确新增组的曝光次数、每组是否两侧同时见到、旧八动作与真实工具监督保留量；不能把同组变体随机拆成训练和测试，也不能仅增加总条数却让关键样本在前400步完全没见到。

建议保持相同底模、提示、损失和训练预算，先测试成对数据及曝光本身的作用，不同时换模型/加新损失。原门槛保留；不因本轮数据审查通过而降低工具联合、追问和认证误用要求。已反复使用的开发集只能用于开发监测，不能宣称独立泛化；真正的保留评测仍隔离，不能拿错题训练。

明确验收目标是：维持旧业务表现的同时，减少未认证调用，改善缺参追问和可用工具选择。**数据复核通过只是启动该对照设计的条件，不是模型达标结论。** 本轮没有GPU训练、Jev请求、新部署、Git提交或推送。
