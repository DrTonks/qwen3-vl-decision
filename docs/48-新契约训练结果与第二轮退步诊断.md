# 新契约训练结果与第二轮退步诊断

2026-10-03。正式实验于北京时间16:09开始、20:38结束，2,940步、两轮完整覆盖已完成；**两个候选均未通过原定门槛，没有合格新模型可部署。** 本轮诊断只重算现有开发预测、读取训练统计并调用本地Node纯函数检查输入与参数处理；没有追加训练、模型推理、Jev调用，也没有运行校准或最终评估。

## 第二轮究竟改错了什么

两轮之间：111题都正确、14题都错误、**0题由错变对、3题由对变错**。3条新增动作错误均在当前服务场景：

|开发题ID|诉求摘要|正确动作|第一轮|第二轮|
|---|---|---|---|---|
|DEV-0019|解释给出的申请状态字段2|tool：状态解释|tool，工具也正确|clarify|
|DEV-0021|本人取消装修计划，要求撤销未审批申请|human：合法但当前无写操作工具|human|refuse|
|DEV-0025|旧号码停机，要求更换本人绑定手机号|human：合法但当前无写操作工具|human|refuse|

这里最关键的是**“不能自动办理”与“请求本身被禁止”不同**。系统没有撤销、换绑工具，应交人工处理并如实说明未接通；不能把合法个人请求直接当造假或越权拒绝。冻结标签没有因此改动。

共17条至少在一轮错误的完整开发输入、可信状态、标签与两轮预测，保存于[development-cases.json](evidence/financial-service-v2-diagnosis-v1/development-cases.json)。该文件明确`training_eligible=false`，只用于诊断，**不得复制到训练集、改写成训练近邻或当作生成模板**。

其余持续错误主要涉及：能力询问被当实际查询，合法但超出现有工具的请求被误拒绝或追问，正文已有编号但模型仍要求补充，未认证公开查询误选工具，以及普通致谢误选追问。这些是诊断分类，不是重新标注。

## 有过拟合迹象，但证据还不足以确证

|观察|第一轮|第二轮|含义|
|---|---:|---:|---|
|轮内平均训练组合损失|0.4543|0.1572|对训练目标的拟合继续改善|
|轮尾100步平均组合损失|0.2642|0.1228|训练末段也仍在下降|
|开发动作负对数似然NLL|0.4984|0.7857|对正确开发标签的概率分配反而恶化|
|开发动作Brier分数|0.1887|0.2332|概率预测整体变差，越低越好|
|错误且最高候选概率≥95%的题数|6|10|更多高置信度错误|

训练损失是随更新计算的“动作CE＋0.75×工具CE”，每个批次输入也不同；它不是固定训练集在eval模式下测得的动作NLL，不能把两列直接相减叫作严格泛化间隙。训练损失下降、开发NLL上升、关键动作退步共同构成**与过拟合或训练分布偏置一致的迹象**，但尚未做多随机种子或独立最终验证。

第二轮相对第一轮准确率差为−2.34个百分点。按32个故事组进行10,000次配对bootstrap，95%区间约为 **[−5.47，0.00]个百分点**；按行独立假设的精确McNemar检验p=0.25。区间含0，样本小且故事变体相关，不能断言“第二轮对所有真实业务必然更差”。我们可以确定的是：**本次这两个检查点没有选出合格候选，继续延长训练缺乏支持。**

概率分析仅使用已有开发logits，未调温度、未选择拒判阈值。最高候选概率不是天然正确率；95%阈值这里只是诊断统计，不能直接成为上线策略。

## 更具体的数据与输入问题

当前服务训练只有574/11,756=4.88%，未来已登录KB场景6,860条，登录前4,322条。数量大并不等于当前服务的动作边界、字段缺失和自然表达覆盖足够。作为训练来源盘点，包含“注销”的32条中human仅2条，包含“手机号”的34条中human仅2条；关键词出现可以是政策咨询、恶意操作或合法办理，**这些计数不等于其中其他标签错误**，只说明需要按完整语义检查覆盖。

结构化字段的分布差异更明确：

|真实目标工具|训练条数|训练带结构化参数|开发条数|开发带结构化参数|
|---|---:|---:|---:|---:|
|申请明细|472|472|5|1|
|状态解释|256|256|3|0|

训练中的这两类工具目标全部带`state.application_id`或`state.status_code`；开发中多数只把编号/状态写在正文。模型可能学到“有结构化字段才调用工具”的捷径，正文表达变化时就追问或误转人工。**这是有数据依据的待验证假设，不是已完成的消融实验。** 本轮没有重新推理“补上字段之后是否改对”，也没有据此扣除原始模型错误。

## 模型组件分数与真实后端结果不能混算

额外只读调用实际Node的`modelInput`和`toDecision`，重建64条当前服务开发题的消息、历史和会话字段，不启动服务器或数据库。结果为：

- **7条的结构化state会变化。** 例如DEV-0009正文已有“申请731”，Node会提取`application_id=731`，而组件评测原输入没有这个字段。现有评测符合宽泛输入合同，但不全是当前Node预处理后的典型输入。
- **2条真实目标为状态解释的题，即使假设模型给出正确动作和工具，也会被现有参数解析器改成clarify。** DEV-0018、DEV-0019的表达不被现有状态码正则识别。这里输入给`toDecision`的是标注动作，用于隔离检查参数处理，不是一次真实模型端到端测试。
- 现有实际聊天入口要求已登录；未登录题属于组件鲁棒性。后端仍有认证拦截，因此模型误选工具2条并不证明已经发生越权读取，但模型组件的错误不能因后端拦截就被算作答对。

证据见[node-grounding.json](evidence/financial-service-v2-diagnosis-v1/node-grounding.json)。该检查的会话是从可见字段重建，不能完全还原真实客户端/数据库会话，也没有验证知识检索、人工工单或实际业务工具执行。

这意味着后续需要两个明确区分的评估层：

1. **组件鲁棒性**：保持当前冻结评估，考察仅正文、缺字段、能力改变和登录前输入。
2. **真实服务流程**：从实际Node构造输入，经模型选择、后端鉴权/参数/工具到最终响应，单独报告原始动作与实际动作。

不能把原评估改成预处理后的输入、覆盖旧成绩，然后宣称这次模型已通过；若进行输入投影对照，应另存版本并明确其为看过开发结果后的诊断，不是新盲测。

## 为什么这次比预计更久，推理是否变快

实际纯训练266.64分钟，全程269.75分钟，超过探针给出的210—240分钟预留。第一轮109.57分钟，第二轮157.07分钟；第二轮有240步超过10秒，P95约12.99秒，最长46.77秒，而第一轮没有超过10秒的步骤。**短探针低估了后续长尾耗时。** 两轮每条数据均出现一次、任务总量一致，日志无法确定长尾来自桌面负载、功耗、温度、调度还是具体批次形状，不能直接归因于硬件故障或模型变大。

|版本|单次动作判别P50|完整决策请求P50|完整请求P95|预测tool次数/128|
|---|---:|---:|---:|---:|
|原始0.8B|81.7ms|166.9ms|184.4ms|81|
|第一轮|101.2ms|102.4ms|217.1ms|21|
|第二轮|92.3ms|93.5ms|199.6ms|19|

完整请求P50下降，很大程度与误触发第二次工具选择的次数减少相符；**不代表LoRA让单次模型前向计算更快**，单动作P50本轮反而比原始更高。三个阶段未做交错重复测速，不能排除系统负载差异。这里不含业务后端或最终回答模型，也没有新版Jev同条件速度；旧Jev结果不能直接拼表。

## 建议的下一步

现在优先处理输入与监督覆盖，而非直接续训第二轮权重，也不据此升级2B。

1. **先补工程契约。** 为Node预处理、状态码/编号解析、鉴权和能力降级建立独立回归测试，明确哪些信息进入结构化state；修复参数解析缺口时也要验证多编号、金额、日期、模糊表达不能被误解析。真实流程与组件鲁棒性成绩分开。
2. **再整理下一版训练数据。** 从政策清单与训练来源出发，复查合法个人请求、仅能力咨询、禁止操作三者的边界，补足当前无KB场景，以及“仅正文有值/结构化有值/确实缺值/多值歧义”等状态组合。可先预算约1,200—2,000条经过独立审核的新增或改写训练候选，而不是翻倍所有旧模板。此数量是准备预算，不保证效果。
3. **保持评测隔离。** 本报告开发原句、ID和错例不给训练作者作模板；训练作者依据业务规则独立出题。新的端到端验收也独立设计。现有校准和最终集保持未评测，不用其标签或错题调方案。
4. **数据和工程检查完成后再定训练对照。** 保留第一轮检查点作研究参考，不部署；下一版优先验证较短预算/较小更新幅度与新覆盖的作用，不直接叠加长训。学习率、预算及新对照方案另行冻结，避免同时改很多变量后无法解释提升来源。

本次没有创建上述训练候选、修改业务后端或启动新实验；交付的是结果核验、可复现诊断和下一阶段依据。既有默认服务配置保持不变。
