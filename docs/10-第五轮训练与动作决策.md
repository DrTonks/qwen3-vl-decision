# 第五轮：客服边界、多轮上下文与动作决策

本轮接着第四轮的不足开展：独立客服泛化证据不足，已有信息是否充分存在标签歧义，CrossWOZ 多轮领域判断弱于 Jev。目标是提高客服下一步决策能力，同时保持公共中文意图能力。不是训练贷款审批模型，也不是训练完整回答生成器。

执行状态以 `results/joint-v5/status.json`、`training-summary.json` 为准。训练未结束前不得把计划当作结果。第四轮源码、配置、数据及结果保留。

## 1. 首 token 与候选输出层裁剪

先把提示、历史、当前问题和可信状态全部交给模型计算，再取最后一个输入位置的隐藏向量 `h`。**首 token 是准备生成的第一个输出 token，不是输入的第一个字；仍须处理完整输入。**

本地 Qwen3-VL-2B 的隐藏维度是 2,048，词表大小是 151,936。普通线性输出层权重 `W` 有 151,936 行，每行对应一个词表 token：

```python
all_logits = F.linear(h, W)         # 完整的 151936 个词表分数
scores = all_logits[candidate_ids] # 取 A/B/C/D 对应的分数
probs = scores.float().softmax(-1) # 只在候选内归一化
```

若 A/B/C/D 各是一个 token，可以直接取四行：

```python
selected_W = W.index_select(0, candidate_ids)
scores = F.linear(h, selected_W)    # 只计算 4 个分数
probs = scores.float().softmax(-1)
```

实际代码还处理 bias、设备与精度，见 `candidate_benchmark.py`。`logits_to_keep=1` 只减少输出的输入位置数，原来仍对最后一个位置计算完整词表；候选行裁剪进一步减少词表维度。候选重排时，A/B/C/D 的业务含义来自当前提示，不能将 A 永久当作某种业务类别。当前候选都检查为单 token，多 token 标签不能直接套用。

在线性输出层下，候选分数数学上相同；有限精度和不同内核仍可能有舍入差异。候选 softmax 是**限定在候选内**的相对概率，不是完整词表概率，也不是“答案正确的真实概率”。需要完整词表中的绝对概率时，不能省略其他词表分数。

第四轮已完成实测：

|指标|完整输出层|候选行输出层|
|---|---:|---:|
|请求 P50|379.97 ms|375.04 ms|
|请求 P95|394.15 ms|385.20 ms|
|P50/P95 耗时下降|—|1.30% / 2.27%|
|543 个开发任务的类别差异|—|0|
|最大候选 logit / 概率差异|—|0 / 0|

每个请求仍执行意图、路由、工具三次前向；12 个请求、三次交替重复。配对平均节省约 7.26 ms，属于单设备探索实验。前面处理输入的 28 层语言骨干、分词、框架调用和数据回传仍在，不能把 151,936 / 4 当成整模型加速倍数。未达到预设 P50/P95 均改善 5% 的门槛，**默认实现不变**。

模型还启用了输入/输出权重绑定，输入嵌入仍可能需要完整权重；不能据此声称能删除整个词表矩阵节省显存。已测实现保留原头，没有测得部署显存收益。

## 2. 工具选择是否还要一次决策

现有实验每条业务请求固定做三次前向：意图、路由、具体工具。第三次重新使用同一输入提问工具候选分类，不是继续生成一长串文字。路由不是 tool 时最终强制工具为 none，但历史基准仍固定计算第三次。

部署可改成路由为 tool 才继续选工具；也可以直接给八个下一步动作候选：

```text
追问 / 交给回复模型 / 转人工 /
查产品 / 查信用分 / 查申请列表 / 查申请详情 / 解释状态码
```

选“查申请详情”就同时确定 `route=tool` 和 `tool=queryApplicationDetail`。保留意图统计时共两次前向；在线只需要动作时理论上一次即可。减少完整前向的潜在收益比输出层裁剪更大，但提示长度、八类任务难度和推理实现都会影响收益，不能预先承诺提速三分之一。

第五轮主实验保留三任务训练。训练后，用所选模型做**尚未专项训练的八动作提示探索**：全部 402 条开发样本核对效果，32 条开发请求、三次交替测速度，结果写入 `results/joint-v5/action-probe/`。这不是已完成的动作专项微调；有效后再做固定预算动作训练及新留出验证，不自动替换原方案。

用户后来提出的 `clarify/retrieve/tool/answer/human/redirect/refuse/close` 是另一套八类业务动作，不能与上面的三类非工具＋五个具体工具混淆。新业务协议及人工验收建议见 [八类业务动作与人工验收](11-八类业务动作与人工验收.md)，不在本轮训练中途换标签。

工具名与参数也要分开：首 token 分类不会自动生成申请编号。完整链路应是：

```text
问题 + 历史 + 登录态 → 下一步动作
→ 从可信状态/对话提取参数 → 校验格式、必填项、登录和记录归属
→ 执行只读工具 → 根据结果决定解释、补问、有限重试或人工
```

已有可信申请编号就直接填参数，不需要再问决策模型；缺编号则追问，复杂抽取才考虑额外模型。“先找到最近申请，再查明细”等多步任务，在取得新工具结果后再做一轮动作决策，并设置调用步数/重试上限。那是获得新信息后的下一步，不是每次机械增加分类。**当前实验不执行真实平台工具，真实执行闭环仍待集成。**

## 3. 数据和政策

|集合|训练|开发|校准|测试|
|---|---:|---:|---:|---:|
|客服业务|4,904|402|402|402|
|MASSIVE 中文|10,725|273|313|2,974|

没有为凑 8,000 条补重复句。核心训练问法仅来自第四轮 train；安全/还款等也只回放 train。新增状态覆盖充分/部分/过期记录、成功空列表、未找到记录、首次超时、重试仍超时、权限失败，以及界面与审批明细边界。上下文覆盖指代确认、用户纠正、无关历史、干扰指令。同一问法的全部状态和变体只属于一个 split。

**4,904 行不是 4,904 个独立问题。** 训练只有 146 个表达组，开发/校准/测试各 21 组，组内高度相关。条件分布、来源和 SHA256 见公开 `results/joint-v5/data-manifest.json`。新开发/校准/测试仍共享编写者、政策、生成器，全部为 `synthetic_unreviewed`。旧测试没有转为训练；已分析过的公共测试继续叫回归，不重新称盲测。

CrossWOZ 来自[官方仓库](https://github.com/thu-coai/CrossWOZ)，训练仅取 train，val 按完整对话分为开发/校准。训练最多每对话三轮、每领域六百轮，排除与 val/test 当前话语规范化重复的训练项；输入仅为当前话语及前六轮历史，不含 goal、dialog_act、后台标注状态和未来回复。这只是五领域子任务，不等于完整 CrossWOZ 系统成绩。revision/哈希见 `data/crosswoz-training-source.json`。

`configs/decision-v5.json` 单独补充“部分记录不算充分事实”和超时策略：首次只读查询超时允许重试一次，重试仍失败转人工。**这是实验选择的业务契约，需要团队确认，不是通用行业规则。** 基础模型、第四轮适配器和第五轮适配器都用新政策比较；原第四轮提示结果保留。

## 4. 训练、选择和恢复

Qwen3-VL-2B、NF4、语言 q_proj/v_proj LoRA r=8，视觉冻结。micro-batch=2，累积=4，常规等效批量约 8；学习率 7e-5，warmup 5%，最多两轮。损失权重：MASSIVE 0.5、CrossWOZ 0.35、业务意图 1、路由 2、工具 1.5。每轮完整遍历，不用放回抽样隐藏覆盖率。

在总步数 25%/50%/75%/100% 评估开发集，约为 0.5/1/1.5/2 轮。选型目标为公共意图、业务意图、路由宏 F1、工具必要子集联合正确率的几何平均；各项不低于同提示第四轮参考减 3 个百分点，人工漏转不增加，CrossWOZ 不低于参考减 3 个百分点。参考模型也参加选择，新训练可能不被采用。

这些是两轮训练中的中途检查点，学习率都按两轮总预算衰减，**不是独立一轮/两轮训练的严格消融**。先用一个种子，有效后再重复；不能把单次提升当作稳定收益。

每 100 个 optimizer step 及正式评估检查点保存：适配器、AdamW 动量、Python/NumPy/PyTorch/CUDA RNG、全局步数、样本覆盖数、协议哈希。学习率由冻结配置及全局步数确定恢复；最多重放上次保存后的不足 100 步。先写 pending 目录，校验完成后原子改名；未完成目录不作为恢复点。恢复只加载本地生成且哈希一致的状态。

评测逐条保存，恢复时核对 ID 顺序，只补缺失项；允许修复最后一条中断写入。操作系统锁阻止两个第五轮执行器同时跑。源码/数据/配置变化会拒绝恢复。CPU 测试验证了不中断与恢复后的下一步参数相同；这不保证不同 GPU 环境逐位一致。

## 4.1 用户同意采用小幅输出层优化后的实现

用户表示即使收益小也希望采用，因此新增独立 `candidate_inference.py` / `infer.py` 推理入口，默认 `--projection candidate`，可用 `--projection full` 回退。**第四轮、正在跑的第五轮训练和正式评分器不改**，保持原始对照口径。

新 `CandidateLinear` 共用原有 Parameter，保留权重绑定和 state_dict 键；正常调用仍计算完整词表，候选调用在上下文内选择所需行，并缓存小矩阵。退出上下文（含异常）恢复完整输出，不为每个请求切换模型模块。用于本项目单设备、文本、eval模式、无生成缓存的推理，不代表分布式/编译/图文推理也已验证。一个模型由一个 scorer 管理；更换权重或适配器后应重建 scorer。

首次遇到每组候选时多跑一次完整输出作启动核对；类别不同、非有限分数或候选概率最大差超过1e-4时，该 scorer 回退完整词表。核对通过不等于证明所有可能输入绝对无差异；还需回归。首请求包含核对成本，不应当作稳定速度。新CPU测试覆盖实际小型Qwen3VL前向、候选顺序、权重绑定、上下文隔离、异常恢复、缓存失效及自动回退。

完整模型的新封装验证排在第五轮流程完成后，避免争抢GPU。`projection_validate --after-v5` 对所选模型的全部业务/MASSIVE/CrossWOZ开发任务做原实现对照，另做12请求×3交替测时；结果位于 `results/joint-v5/projection-inference/`。没有因为收益小而设最低速度门槛，但正确性门槛仍保留。新的GPU结果未出前，旧543任务证据只能归于原候选裁剪实验，不能冒充新封装/新权重已验证。

训练结束、GPU空闲后可测试独立入口（它会检查同一GPU工作锁）：

## 5. 独立 500 条人工验收

当前缺少独立样本和标注人，不能用同一生成器再造 500 行就称“独立验收完成”。`.local/review/joint-v5/independent-acceptance-template.csv` 目前只有表头；开发待审表 `development-review.csv` 与它分开。

建议未看模型预测的成员准备脱敏场景：100 条产品/信用/申请查询，100 条界面与审批边界，100 条多轮指代/纠正，80 条工具结果/信息充分性，80 条安全争议/人工，40 条模糊与范围外问题，共 500 条，按主要场景只计一类。同源对话/改写保持同组。

两位成员各在独立副本盲标，之后仲裁；第二人不要看第一人标签。先固定政策，记录分歧。冻结样本与标签哈希后才运行模型和 Jev；不能看到某模型答错后修改标签抬分，歧义需单列。

后续顺序：有效场景训练与检查点对照 → 开发错例复核 → 校准与动作专项对照 → 第二种子 → 独立验收 → 再决定扩至约 8k、增大 LoRA 或接入平台。长训练无法弥补错误标签和缺失的独立验收。
