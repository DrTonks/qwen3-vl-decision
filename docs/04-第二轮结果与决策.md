# 第二轮实测结果与下一步决策

日期：2026-09-26。已完成目录重组、数据扩展、BF16/NF4 对照、120 步 QLoRA、独立温度校准、完整测试和发布检查。此次是探索性研究，不是生产验收。

**结论：本机可以训练，但本轮适配器不能替代 Jev 做贷款客服路由。** 公共中文意图准确率有改善、概率也更可信；最相关的业务路由几乎没有改善，还出现工具链退化。继续盲目增加训练步数的依据不足，应先修正任务目标和业务标注，再决定训练投入。

## 1. 数据和计数口径

- MASSIVE 官方中文 test：2,974 条，60 个候选。Jev 有两次 HTTP 520，成功 2,972 条；Qwen 全部完成。
- CrossWOZ：官方 test 中 200 个单领域用户轮次，五类各 40 条，输入含之前 6 轮文本。不是原始完整任务成绩。
- 业务：72 条、18 个场景组，来自第一轮合成样本，尚未人工复核，属于回归测试。
- 训练池：公开 train 1,715 条、业务 48 条；开发 273+16 条，校准 313+56 条。组和规范化文本隔离。

表中 Jev 的 MASSIVE 准确率按成功请求计算。把失败也算错为 **2,320/2,974=78.01%**；成功请求为 **2,320/2,972=78.06%**。其他测试没有请求失败。原始预测、错误明细、分组区间和所有字段见 [机器指标](../results/phase2/metrics.json) 与 [汇总表](../results/phase2/summary.md)。

## 2. 分类与路由结果

|任务|Jev|Qwen BF16，精简提示|Qwen NF4，未训练|NF4 + QLoRA|
|---|---:|---:|---:|---:|
|MASSIVE 意图准确率|78.06%|58.64%|55.01%|65.47%|
|CrossWOZ 领域准确率|87.00%|76.00%|59.00%|64.50%|
|业务意图准确率|93.06%|59.72%|59.72%|66.67%|
|业务路由准确率|97.22%|37.50%|43.06%|44.44%|
|业务工具准确率，含 none|97.22%|70.83%|75.00%|75.00%|
|真正需工具时，路由和工具同时正确|20/20|0/20|9/20|2/20|
|必须转人工的漏判|1/20|0/20|2/20|3/20|

QLoRA 在 MASSIVE 上相对未训练 NF4 增加 **10.46 个百分点**，按规范化文本组 bootstrap 的 95% 区间约为 **[9.04,11.85]**。业务路由仅增加 **1.39 个百分点**，按场景组区间为 **[-9.72,13.89]**，没有可靠改善证据。这些区间只描述当前样本差异，不包括多次训练种子的方差。

业务全字段都正确的数量为 Jev **65/72**、QLoRA **20/72**。第二轮工具经过门控、人工标记由路由推导，不能与第一轮四个字段独立预测的总分直接混为一谈。

**75% 的工具准确率为什么仍然很差？** 因为大量样本本就应该输出 none。真正需要查询记录时，QLoRA 只有 2/20 条正确完成“路由到工具并选对工具”。与未训练 NF4 相比，这项从 9/20 下降到 2/20，而总体工具准确率仍为 75%。这正是需要同时报告业务子集和联合链路指标的原因。

**零漏转不一定安全。** 精简提示的 BF16 没漏掉人工标签，却把很多正常问题也转了人工，整体路由只有 37.5%。QLoRA 的 3 次漏转包含“普通排查已失败的页面/数据冲突”和两条“查询他人申请详情”。实验没有执行工具；真实系统必须独立检查所有权，不能依赖模型自觉拒绝。

## 3. 哪些尝试成功，哪些失败

成功的是：本机完成了真实梯度训练，公共中文意图区分和概率损失有所改善；模型、数据、训练和测试可按版本复核。

失败的是：精简提示没有达成“更快且保持业务质量”。第一轮原始 BF16 路由为 63.9%，第二轮精简提示下降到 37.5%；即使训练后也只有 44.4%。第二轮同时改变提示内容与任务调用流程，没有完整因子实验，不能把下降全归因于某一个改动。当前版本应保留为研究对照，不能替换原业务方案。

量化也不是无代价：NF4 在本机节省显存，却比 BF16 更慢，并降低公开任务准确率。训练补回了部分损失，但 CrossWOZ 64.5% 仍低于未量化 BF16 的 76%。没有图片测试，不能推导多模态能力得到了保持或提升。

本次目标函数等权平均公共与业务的开发 NLL，业务内部又混合意图、路由和工具。它不等于专门优化路由或降低人工漏判。开发日志中业务 66.7% 是 16 条样本拆成 48 个问题后的混合准确率，不应误读成路由准确率。

## 4. 延迟与资源

|任务的完整预测流程|Jev P50 / P95|BF16|NF4|NF4 + QLoRA|
|---|---:|---:|---:|---:|
|MASSIVE|492 / 559 ms|88 / 92 ms|104 / 109 ms|113 / 119 ms|
|业务|491 / 543 ms|185 / 207 ms|223 / 327 ms|234 / 356 ms|
|CrossWOZ|493 / 558 ms|50 / 69 ms|77 / 87 ms|80 / 91 ms|

Qwen 确实更快，但当前准确率差距不符合“仅略低”的前提。业务比单意图更慢，因为要做两至三次前向。API 含网络且本轮三个并发请求，本地逐条运行；这是单次实验的热启动端到端延迟，不是相同硬件上的架构比较，也不是服务化吞吐保证。

本地推理 allocated 峰值：BF16 约 4.026 GiB、NF4 约 2.093 GiB、带适配器约 2.099 GiB。BF16 修正候选后的重跑只重新处理 MASSIVE，其余两组复用未受影响的原始结果，来源哈希单列保存。显存指标不含全部驱动和桌面占用。

训练：r=8，q_proj/v_proj，1,605,632 个可训练参数；120 次更新，每次累计 8 个分类问题，共 960 次。478 次业务、482 次公共；按相同种子重建采样器，涉及 48 条业务原文和 423 条公共原文，不能说完整训练了 1,715 条。耗时 504.48 秒，allocated 峰值 3.628 GiB。按预先固定开发 NLL 选择第 120 步。适配器约 6.44 MB，不包含基础模型。

## 5. 校准改变了什么

|任务与模型|温度 T|NLL 校准前 → 后|ECE 校准前 → 后|准确率|
|---|---:|---:|---:|---|
|MASSIVE，未训练 NF4|3.740|5.134 → 2.241|0.322 → 0.064|仍为 55.01%|
|MASSIVE，QLoRA|1.100|1.589 → 1.563|0.056 → 0.018|仍为 65.47%|
|业务路由，QLoRA|1.107|1.453 → 1.388|0.301 → 0.305|仍为 44.44%|

可见校准不保证每个指标都改善。业务路由 ECE 略变差，即使 NLL 降低；两个指标衡量的方面不同。独立校准集较小，仍存在分布差异。

固定置信度阈值 0.9 时，校准后的 QLoRA 业务路由接受 13/72 条，当前 13 条都对，但覆盖仅 **18.1%**。这不足以证明真实业务零风险。MASSIVE 接受 637/2,974 条，其中错 48 条；不能只报被接受部分的高分而不报覆盖率。

工具温度拟合仅有 15 条被路由器选中的校准样本，并碰到搜索下界 T=0.05。它只作为实验记录保存，**不能作为生产置信度参数**。needs_human 是由路由推导的字段，没有独立概率，未对它伪造校准结果。

## 6. 为什么 Jev 看起来很高

业务 97.2% 来自四类路由、明确政策、72 条合成表达和 18 个场景组，主要反映规则遵循。它不是“所有中文客服都能达到 97.2%”。公开 60 类意图下为 78.1%，更能显示复杂意图边界的困难。第一轮公共子集是 117 条、59 候选，不能把两轮变化仅归因于样本量。

Jev 原生 choice 接口与我们的提示式首 token 方案在任务适配上不同。我们没有其内部训练证据，不能宣称它用了某种特定算法，更不能依据高分推断它作弊。此次没有把 API 输出用于训练或校准；所有监督来自公开原始标签或自建业务标签。

## 7. 错误尝试、费用和可信度

额外候选 `iot_hue_lightother` 由单元测试发现后，61 类运行被归档，修正为官方 60 类重跑 MASSIVE。未受影响的业务和 CrossWOZ 预测复用，附哈希。首次 NF4 加载失败以及两步训练冒烟另有记录，冒烟适配器没有用于正式训练。

本轮实际记录 6,220 次 Jev 请求，包括需要废弃的候选错误运行；成功 6,218 次，失败 2 次，失败未静默重试。成功响应报告输入 8,844,598 token、输出 3,475,666 token。复用的文件不重复计数。详见 `results/phase2/api-usage.json`，这不是账单，失败请求计费情况未知。

单随机种子、少量合成业务监督、已经看过的业务回归、可能的公开数据预训练接触，都限制结论。模型选择没有看 test，但本轮结果现已用于提出下一轮开发方向；未来最终验收需新建独立业务测试集。

## 8. 追加的开发集提示对照

发现业务失败后，保留全部测试成绩，使用同一个已训练适配器，在开发集做四种提示对照，没有再训练或重跑 test。业务仅评留出的 16 条 route，公共集评 273 条 intent。

|提示|业务 route（16 条）|MASSIVE intent（273 条）|
|---|---:|---:|
|冻结版本|31.25%|72.16%|
|候选恢复英文标识|37.50%|70.33%|
|“候选字母”改为“候选符号”|31.25%|72.89%|
|两项都改|37.50%|69.60%|

英文标识只多修正 1 条业务开发样本，公共集反而下降；措辞修改在公共集多修正 2 条。不能证明某个微小提示修正就能解决路由，更不能选择开发分最高的一项后直接宣称测试也提高了。开发日志中的“业务混合准确率 66.7%”与这里路由专项的低分，也说明混合总分掩盖了主任务问题。

代码为 `src/qwenlab/ablate_prompt.py`，结果在 `results/phase2/development-ablation/`。这些是发现问题后的探索证据，不是新的独立验收结果。

## 9. 建议接下来怎么做

1. 先人工审核路由政策和样本，补充真实脱敏业务的登录、所有权、缺少编号、工具不可用、页面/后台冲突和争议场景；按场景组建立新的训练与盲测集。
2. 把路由作为独立目标，开发选择优先看必须人工漏判、真实需工具的联合正确率和路由准确率。通用意图与 CrossWOZ 作为迁移回归，不再用一个混合总分代替业务目标。
3. 在开发集上比较保留标签标识的提示、明确状态表示和简单的权限/安全前置规则，先确认推理方案可用，再增加训练量。训练时继续随机候选顺序。
4. 如果近期要继续项目接通，可让 Jev 进入带后端权限校验和人工兜底的受控验证；Qwen 保留研究线。当前没有足够证据直接替换，也没有理由仅凭一次小规模训练否定这条路线。
5. 业务文字路由稳定后，再加入实际截图与多模态回归，重新测显存、时延和误判，不能直接把当前文本成绩外推到图片。

本次没有上线模型、执行金融工具或推送 GitHub。完整复现、私有资料排除和发布命令见 README；公开训练过程见 [过程文档](03-工程化与微调校准过程.md)。
