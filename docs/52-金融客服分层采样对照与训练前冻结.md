# 金融客服分层采样对照与训练前冻结

2026-10-04，承接报告51。新的有限预算采样对照已完成CPU冻结：同一13,242条池、两份各3,200次曝光清单及完整分词账本；40项合成测试、全池盲筛重放和实际tokenizer重放通过。**没有启动训练、加载模型权重、请求Jev或改变部署**。训练配置保持`training_enabled=false`；候选池的`split=train`表示拟用于训练的分区，不能等同于已经获准运行。

## 要验证什么

问题是：相同模型、数据池和业务样本曝光预算下，增加当前服务场景的训练曝光，是否比全池均匀抽样更有效，同时不损害旧业务和安全边界？

两臂都从官方Qwen3.5-0.8B创建全新LoRA，不从此前未通过门槛的适配器继续训练。对照使用同一政策、提示、候选层、优化器、学习率序列及400步预算；唯一允许不同的输入是已冻结的抽样清单。分层策略同时改变场景比例、故事组权重和重复率，因此结论只能归因于整套采样策略，不能说已经证明某个单独比例最优。

本轮是小预算的方向检验，不是完整覆盖训练，也不承诺400步达到Jev。不要直接修改旧两轮执行器的步数、数据路径或抽样函数；旧实验需要保持可复现。

## 固定对照和曝光预算

在正式排程生成前固定种子20261004。抽样使用局部`random.Random`；将来训练前另行重置torch、CUDA、NumPy和Python的初始化种子，两臂检查初始适配器参数SHA一致，抽样不得消耗模型初始化随机状态。独立审核此前用旧种子20261003做过纯元数据容量测试，它不是模型选种子，也不是本轮正式排程。

上表来自实际本地tokenizer编码与冻结清单核算，不是GPU运行。分层组补齐后的token量仅高约0.71%，但真实tool曝光多21.84%、非空tool microbatch从561增至663，所以不能仅凭token接近就断言两臂速度一致。全池动作输入最长634、工具输入最长682 token，全部低于2,048，无截断。

uniform对按ID排序的全池一次洗牌，取前3,200行，不按组均衡。分层组每20行固定9当前Node、3当前组件、5未来知识、3未登录，块内随机交错；每层先轮转来源组，再在组内轮转洗牌行。20条配额块与8条有效batch在40行/5步重新对齐，不要求每步严格满足60%/25%/15%。

两臂共同硬上限为单行4次、跨层全局来源组16次。本轮真实排程不超过上限，部分分层行达到4次；若未来输入变动导致容量不足，应失败，不借用其他层配额、静默跳过uniform抽中的记录或换种子。不会通过给相同故事加不同层前缀来拆散组。

两臂只有一小部分数据被曝光：这是固定预算抽样对照。分层组覆盖更少的独立行/组、有更多重复，必须把改善与过拟合风险一起看。每个曝光的ID、来源行SHA、来源组、层、步数、microbatch、出现次数均保存为账本。200步诊断直接使用冻结清单前1,600行，不重新抽样。

## 训练与评估协议

参数详见[冻结配置](../configs/financial-sampling-study-v1.json)。有效batch8、microbatch2、累积4；BF16冻结底座、FP32语言LoRA，r8/alpha16/dropout0.05，目标为现有语言模块。AdamW学习率5e-5、weight decay0.01、betas0.9/0.999、eps1e-8、梯度裁剪1；SDPA、不启用KV cache、非reentrant梯度检查点。foreach/fused等开关已显式记录，将来执行器不得依赖未声明默认值。

warmup100步，占本次预算25%；之后线性衰减到400步。采用原公式但总步数固定400：第200步3.35e-5，第400步约1.667e-7。原始业务行始终是loss分母：`sum(CE_action + 0.75 * I_tool * CE_tool) / 8`，不把工具行除以1.75，也不把工具loss单独按tool数量平均。

工具比例不同使同样3,200条业务曝光对应不同监督任务和token预算。本轮分词统计按实际microbatch内action、真实tool分别补齐到各自最长输入；不跨microbatch重组tool。token数是计算量代理，不能当精确FLOPs。未来实测还需报告显存、每步耗时、总时长及暂停区间。

先uniform、后stratified串行执行。200步只诊断，不据此改比例、超参或淘汰较差臂；400步才有资格进入选择。沿用原开发门槛全部字段，包括人工召回、额外人工漏判/误拒绝、工具联合正确率、不可用知识/工具和未登录tool限制，不放宽。仅一臂通过就选择该臂；两个都通过则按macro-F1→工具联合准确率→完全平局优先uniform选一个；两个都失败则终止，不自动增加训练时间。

旧开发集128条、32组已参与诊断，只能称开发回归，不能重新包装成盲测。新训练前需要同提示、同准备方式的base参照；旧速度数据不能直接作为配对测速。只有选出的合格臂进入校准，温度/阈值冻结后再对选中模型和base做一次最终评估，禁止根据最终错例调整本轮训练。单种子结果和故事组bootstrap不反映跨训练种子方差，更不代表真实用户上线效果。

在qwen根目录使用现有D盘环境运行以下验证。它们不会训练；完整盲筛需要本机保留已索引的历史来源，分词需要本地Qwen3.5-0.8B tokenizer文件及对应环境。哈希不符或来源缺失就失败，不能跳过后声称复现成功。

```powershell
. .\scripts\use-env.ps1
.\.venv-qwen35\Scripts\python.exe -m unittest tests.test_financial_sampling_data tests.test_financial_sampling_plan tests.test_financial_sampling_freeze

```

默认`sampling_data verify`只核验来源/文件SHA，`--replay`才完整重做盲筛和分流；默认`sampling_freeze verify`重放计划、账本和已保存长度的统计，`--tokenize`才重新编码所有输入。最终验收使用两项完整重放，不能只看默认验证通过。

首次生成命令如下，当前目录已经存在，重复运行会拒绝覆盖。需要变更数据/配额时另建经过审核的新版本，不能删除旧证据后改同一版本：

```powershell

```

## 后续GPU执行与时长预估

本轮产物是CPU数据和排程工具，**新的GPU执行器尚未实现，不能拿旧启动命令运行本实验**。下一步需要一个独立版本执行器，直接消费冻结ID清单，在恢复时保存并核验精确步数游标、优化器、RNG、协议和清单SHA，不重新洗牌；每50步及用户暂停时在完整优化器步后原子保存。

工程复核后先各臂25步、共50步的训练专用探针，验证显存、损失、真实暂停/恢复与实际速度；探针适配器丢弃，正式两臂从同初始化重新开始。先前2,940步纯训练约266.64分钟，对800步粗略折算约73分钟；加探针、加载、评估、保存和桌面长尾可先预留90—120分钟。**这是历史估计，不是本轮实测**，探针完成后应按实际token任务量更新，不能承诺效果或精确完成时间。

本轮未改App、后端政策/默认provider，也未启动数据库、自动化、提交或推送Git。
