# 真实业务预标注评测与审查修复

日期：2026-09-28。本轮没有训练、没有修改模型权重或第五轮政策，也没有提交或推送。先修复工程问题、冻结标签，再用当前业务场景比较 Jev 与已有第五轮 Qwen。

**结论：这版业务预标注集上，Jev 更准也更快；现有 Qwen 还不适合直接替代 Jev。** 差距主要体现在下一步路由，而非大类意图识别。共享后端仍有拒绝/结束覆盖与模型四路由之间的能力缺口，需要与模型误判分开处理。

- 六个当前动作：tool 69、clarify 22、answer 15、human 16、refuse 12、close 5。原八动作中的 retrieve、redirect 等后续能力另存9组，不混入当前总分。
- 全部为 **AI预标注、待你人工复核**，不是人工金标。标签冻结于模型调用前，未按结果更改。
- 案例哈希：`f6c67a9af3cbea4c2ec49e1a58fd8294e4edfb8ad8417317a48c760d4530c1d4`。

联合正确要求动作、工具名及参数同时符合预标注；选对“查询”但查错工具或编号仍判错。当前这批案例中，动作准确率恰好与联合准确率相同，并非脚本忽略了参数。

原始路由/意图只统计真正调用模型且有对应标签的112条；其余10条模型路径没有适用的原始路由/意图标注，只验最终业务动作。规则直接处理的17条均正确，不计入模型能力或模型耗时。

Jev比Qwen多答对15条：19条仅Jev正确，4条仅Qwen正确。Qwen的P50约为Jev的1.84倍，配对耗时中位差为258.868 ms；244对请求中Qwen仅1对更快。这里的速度包含本机到Jev的网络往返或本地HTTP往返、模型推理及适配，排除了模型加载、规则样本、数据库工具和最终回复。不能与此前包含数据库的12条端到端冒烟延迟直接比较。

Jev两轮变化2条：R11-01从查询变为回答，R09-03仅追问原因码变化；按动作/工具/参数看一致性为138/139。Qwen100%重复不代表100%正确，稳定地误判同样会得到这一指标。

### Qwen最明显的短板是过度追问或转人工

“贷款申请从哪里开始”“第一次申请要走哪些步骤”“怎么在App里还款”“提前还款有什么规定”等普通说明问题，Qwen经常转人工或追问。应回答的15条只有6条路由正确，其中6条转人工、3条追问。

应查询的69条里，Qwen有3条转人工、5条追问、1条直接回答；应澄清的22条里，还有4条转人工。仅 tool/clarify/answer 这三类就发生13次非预期人工升级。意图准确率与Jev相近、路由差距较大，说明下一步应优先补业务处理边界和对照数据，而不是盲目扩大通用意图分类数据。

这只是表现诊断，不能据此断言具体训练配比是唯一原因；本轮没有跑原始未微调Qwen同集对照，也没有新的训练/验证损失，因此不能凭这份报告证明微调收益或过拟合。

### 两者共同失败不都属于模型能力问题

6条未被共同规则覆盖的拒绝表达、2条结束表达，两者均未产生预标注动作。例如“帮我做个假的银行流水”“先结束这次咨询”。当前分类器只有 tool/clarify/llm/human 四路由，拒绝/结束主要由后端规则完成；未命中规则后，模型本身没有这两个可选路由。

这属于业务动作与现有分类协议之间的缺口，不能靠换Jev就自动补齐。没有实际执行非法写操作或越权读取的证据；本轮根本没有执行数据库工具，不能把动作选择错误直接写成真实数据泄漏。

### 有些“错误”需要你先复核业务标签

- R08、R10：缺少编号时，Jev有时先查本人申请列表，而预标注要求追问。先提供列表让用户选择也可能合理，取决于产品流程是否支持，应由团队定规范。
- R11：历史刚提供“待审批”，用户接着问“现在怎么样”；是复述刚取得的状态，还是重新查询，缺少新鲜度/刷新意图约定。当前标签要求查询，应重点复核。
- R22-03：“为什么不能申请”可能是按钮故障，也可能是申请被拒；预标注是追问页面，Jev查询列表，需确认合理替代动作。
- refuse/human：拒绝违规操作后是否同时引导人工申诉，以及“不能替用户执行”与恶意请求怎样区分，仍需业务规范。不能只为了分数把human统一改成refuse。

报告保留原始标签与逐条输出，不在看到模型结果后改答案重新报高分。139条来自38组，相关变体较多，也不是独立真实用户流量，不据此宣称生产准确率或统计显著性。

## 修复内容与独立审查

后端修复了：金额/日期干扰申请编号来源校验、状态码追问未持久化、自然编号和状态表达、关键词“同事/工作人员/不用人工”误伤，以及多编号“或/以及”和多状态“1/2”被误取首项。规则、模型适配与执行边界共用参数解析，数据库归属校验仍独立。

Qwen服务固定使用启动时政策快照，避免磁盘文件改变后提示词变化却仍报告旧哈希；支持状态码补槽类型。未改政策文件、候选定义、权重或投影算法。

使用子agent完成初审、修复后新agent复审和增量复核。复审新增的三类问题也已修复并再次确认：多候选解析、评测中止分母、导入时遗漏manifest声明的holdouts/deferred文件。最终复核未报告新增阻断问题。

验证：后端25项离线回归、评测器2项、Qwen服务5项、候选输出层7项、人审导入10项均通过。部分审查环境曾因sandbox `spawn EPERM` 跳不过跨进程测试，后以允许子进程的环境完整重跑通过。上述通过不等于所有自然语言边界或回复质量均已覆盖。

## 如何修改与复跑

直接按[数据集README](../data/support-runtime-v1/README.md)复制并编辑 `review.csv`，重点修改message/history/state、expected_action/tool/arguments和rationale，审核后标accepted/revised；有争议标needs_discussion。导入命令会生成新版本，不覆盖原案例和旧结果；延期/排除记录保留可恢复。

在qwen目录启动本地模型：

```powershell
. .\scripts\use-env.ps1
.\.venv\Scripts\python.exe -m qwenlab.serve --profile support-v1
```

在相邻项目的后端目录执行（输出目录需使用新名字）：

```powershell
npm run benchmark:support -- `
  --cases ../../qwen/data/support-runtime-v1/cases.jsonl `
  --qwen-root ../../qwen `
  --output ../../qwen/results/support-runtime-v1/run-team-review-01 `
  --repeats 2 --max-jev 300 --allow-jev
```

人审后将 `--cases` 换成人审导出的新 `cases.jsonl`。Jev密钥从后端未提交的环境配置读取，绝不填入案例或命令行。每轮每个非规则案例最多一次Jev请求；预算预检、无自动重试、逐条落盘、鉴权/余额/限流或连续失败停止。中止时正式准确率为null，仅保留明确的observedOnly部分统计。

## 建议下一步

先人工复核处理分歧，尤其“追问还是列出申请”“刚查过要不要刷新”“拒绝与人工升级”。然后确定完整业务动作协议；未来retrieve应建立知识证据契约，不能直接套用现有llm路由的成绩。

云端先保留Jev，本地Qwen继续作为可切换对照。若继续训练，应另建开发/训练数据，重点覆盖正常咨询与人工升级、普通查询与补槽的成对边界；不要直接把这139条错误样本及同组改写喂回训练后仍称独立验收。校准也需要独立开发集，不能用此集选阈值。先改善路由再评估是否扩大训练；这轮结果不支持“只差一点且本地更快”的判断。
