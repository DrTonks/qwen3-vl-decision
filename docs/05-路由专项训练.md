# 第三轮：专门训练业务路由

## 为什么上一轮业务指标不好

首先区分两个比较：

|比较|路由正确数|解释|
|---|---:|---|
|第一轮原始提示、BF16|46/72（63.89%）|原始方案参考|
|第二轮精简提示、BF16|27/72（37.50%）|同一基础模型在另一套提示协议下明显退化|
|第二轮精简提示、NF4|31/72（43.06%）|第二轮训练前基线|
|第二轮精简提示、NF4 + 混合 QLoRA|32/72（44.44%）|训练仅多对一条，不能说微调使路由准确率再次下降|

另一个真实退化是：真正需要工具的 20 条中，“路由和具体工具同时正确”从 9 条降到 2 条；必须人工的漏转从 2/20 增加到 3/20。总分可能掩盖关键链路损失。

根据原种子重建 960 次训练抽样，公开和业务意图共 643 次，工具 166 次，**路由仅 151 次（15.73%）**。原训练目标平均优化不同任务的候选交叉熵，选检查点又平均看公共意图与业务混合 NLL，没有以路由作为主目标。因此公开意图提升不能证明路由学习充分。

数据本身也不足：业务训练 48 条，只有 12 个独立场景组。它们是合成、尚未人工复核的标签。登录与未登录、本人和他人、已有充分状态和需要查询，看似类似的句子可能要求不同路由；多做普通意图分类无法替代这种条件决策训练。

提示敏感、训练目标错位和数据覆盖不足都是有证据支持的排查方向，但不能把所有差异归因于一个因素。第二轮开发集提示消融只说明恢复候选英文 ID 有小幅帮助，未证明这就是全部原因。

## 本轮预先固定的对照

本轮保留原有全部代码与结果，新增 `src/qwenlab/route_v3.py` 和 `configs/route-v3.json`。先恢复第一轮完整业务提示：完整政策、原始 JSON 格式、候选英文 ID 和候选符号指令；训练前后使用相同提示、相同 NF4 推理设置。

1. 从原始 Qwen3-VL-2B-Instruct 重新开始，不叠加第二轮适配器。
2. 只训练 `tool / clarify / llm / human`，不训练普通意图或具体工具名。
3. 使用原 48 条训练样本，候选顺序逐条随机打乱；120 次优化器更新，每次累积 8 条，全部 960 次抽样服务于路由。不是 960 条新样本。
4. 语言注意力 `q_proj/v_proj` 上 QLoRA：r=8、alpha=16、dropout=0.05、学习率 0.0001、warmup=12、AdamW、梯度裁剪 1.0。基础模型和视觉分支冻结；`visual`、`lm_head` 不做 4bit 量化。
5. 保留第 40、80、120 步适配器。每个检查点在新进程中重新加载，按实际部署精度评估，避免训练准备阶段部分参数转 FP32 影响检查点比较。
6. 只用 16 条开发样本选择：优先宏 F1；相同则少漏转人工；仍相同则低 NLL。未训练基础模型也参与选择，不能强行宣布训练模型最好。
7. 选择冻结后，分别评估匹配基础模型和所选模型的 56 条校准、72 条回归。温度仅用校准集拟合，不改变类别，不用测试选择温度或检查点。

四个集合场景组互斥；但旧测试已在之前分析过，所以仍是探索性回归，不能当作全新盲测。业务数据量没有变，本轮隔离的是路由专项训练的作用。与第二轮的差别同时包含提示、抽样目标、检查点选择，不能把跨轮差值全部说成 QLoRA 单项收益；本轮训练前后对照才是主要比较。

训练类别为 tool 12、clarify 8、llm 12、human 16 条，采用逐条均匀随机抽样，没有类别加权或新的样本生成。开发集只有 `explicit_human / injection_tool / status_unknown / ui_unverified` 四组、每组四条。这个覆盖范围不足以代表真实业务，也是本轮不能直接作为上线依据的原因。

## 运行和产物

在已完成第二轮环境与数据准备的项目根目录执行：

```powershell
. .\scripts\use-env.ps1
.\.venv\Scripts\python.exe -m qwenlab.route_v3 run
.\.venv\Scripts\python.exe -m unittest discover -s tests -p "*.py" -v
.\.venv\Scripts\python.exe -m qwenlab.publish --export
```

已有第三轮输出时命令拒绝覆盖；复现完整训练可在新的项目副本中准备数据与模型后运行。Git 发布不包含模型、适配器或个人学习文件。

公开 `results/route-v3/` 包含预先配置和代码哈希、训练损失、适配器配置与哈希、各检查点开发集预测、选择依据、校准和回归逐条预测、指标及错例。实际适配器位于 `.local/checkpoints/route-v3/step-*`。没有新增 Jev API 调用，也没有用 Jev 预测训练。

延迟只衡量一次路由前向，不含加载，不代表“路由 + 工具选择 + 最终回答”的完整客服耗时。工具路由正确也不代表具体工具名和参数正确。本轮未测试图片、普通意图保持能力或完整工具链路。

## 结果

实测已完成，**专项训练没有提高旧回归准确率**。按预先规则选出第 40 步，未根据测试改选第 80/120 步。

|部署式开发集|正确数|宏 F1|NLL|
|---|---:|---:|---:|
|基础 NF4|7/16|0.338|2.815|
|第 40 步，选中|7/16|0.438|2.460|
|第 80 步|7/16|0.386|5.806|
|第 120 步|7/16|0.403|6.629|

训练损失接近零，但所有检查点开发准确率仍只有 7/16，后期 NLL 反而明显升高：模型在开发错误上更加自信，呈现过拟合迹象。扩大相同小数据的训练步数不是合理修复。

|72 条旧回归、18 场景组|原始提示 NF4 基础模型|同提示 NF4 路由专项 QLoRA|
|---|---:|---:|
|路由准确率|40/72（55.56%）|34/72（47.22%）|
|宏 F1|0.484|0.467|
|必须人工漏转|6/20|6/20|
|非人工误转人工|12/52|10/52|
|需要工具时路由正确|20/20|9/20|
|需要追问时路由正确|3/12|6/12|
|应交回复模型时路由正确|3/20|5/20|
|单次路由 P50 / P95|107 / 121 毫秒|113 / 125 毫秒|
|校准前 NLL / ECE|2.007 / 0.283|1.427 / 0.334|
|校准后 NLL / ECE|1.365 / 0.161|1.138 / 0.273|

训练后的路由少对 6 条，即 -8.33 个百分点；按场景组做 2,000 次 bootstrap 的 95% 区间为约 [-27.78, +6.94] 个百分点。小样本不能证明未来必然退化，但本次没有获得可接受的训练收益。Jev 在此前相同 72 条回归中为 70/72（97.22%），本轮未再次调用；它仍不是新业务数据上的产品准确率。

原始提示 NF4 55.56% 与第二轮精简提示 NF4 43.06% 的差异说明提示协议值得认真保留和对照；本轮未重跑全部第二轮工具流程，因此也不能据此宣称整个客服系统已经提速或恢复。

基础模型/专项模型的校准温度分别为 1.835/1.598，均未碰搜索边界。专项模型校准后置信度至少 0.9 的样本有 16 条且全部正确，覆盖率仅 22.22%；不能据这个很小、已经看过的样本建立生产阈值。校准前后路由准确率完全不变。

训练 120 步耗时 356 秒（约 5.9 分钟，不含模型加载和后续评估），训练参数 1,605,632，峰值 allocated 3.623 GiB、reserved 4.072 GiB。本地电脑可以完成这类小规模 QLoRA；当前瓶颈是数据覆盖与决策设计，而非显存不够或没有执行参数更新。

## 错误说明了什么

- **规则例外没学到**：`status_reject` 与 `status_approved` 的 8 条，标签要求调用状态解释工具，专项模型全部选 llm。原政策有“状态码 0/1/2 必须用解释工具”的特例，但训练组没有这些直接例子。模型容易把它们套进“已有充分事实则直接解释”的一般规则。单靠长提示写出例外并不足够。
- **缺失与充分状态没有区分稳**：`ui_pending` 已有“同产品申请审核中”的禁用原因，4 条仍全部被交给人工；`ui_empty` 已给出未填贷款用途，4 条被分到追问或人工。模型没有稳定利用已有结构化状态。
- **人工边界仍遗漏**：未解决的前后端冲突漏转 2 条、疑似身份盗用漏转 1 条、他人隐私记录漏转 3 条。换成专项目标并未消除权限和风险类错误。
- **开发集不代表这些难点**：开发人工组只有明确要求人工，开发 llm 组是未知状态码解释，缺少已知禁用原因、他人记录、争议等边界。仅按这四组选择，无法保证回归质量。

完整逐条预测和混淆矩阵见 `results/route-v3/`。未通过修改旧测试标签、换测试集或测试后挑检查点美化结果。

## 后续如何改进

下一轮应先由业务成员复核政策，再补充独立场景的成对样本：相同诉求分别设置登录/未登录、本人/他人、工具可用/不可用、已知状态/待查询、普通咨询/扣款争议，以及追问后的多轮状态。划分必须按场景或会话组，不能把同一模板的改写分到训练与验收两边。

尤其需要确认“已经给出状态码仍必须调用解释工具”是否确为产品要求。这种固定映射和权限前置检查可以由确定性代码完成，没必要全部交给小模型学习。若调整业务契约，应发布新版本、重新标注和统一重测所有方案；不能只为本轮模型涨分改标签。

建议后续按顺序推进：政策与确定性前置检查 → 数百至千条经复核、覆盖状态反事实的路由样本及更丰富开发组 → 未见场景盲测 → 专项 QLoRA → 独立置信度校准。数据量是规划目标，不是已经完成的数据建设，也不保证达到 Jev 水平。当前不继续在这 48 条上堆步数，不采用本轮适配器替代已有效果更好的方案。

正式验收须覆盖“路由 + 具体工具 + 参数 + 执行前权限检查”。权限和工具可用性由后端强制校验，不能依赖模型自觉。模型输出 human、tool 只是决策建议；这次实验没有连接或执行真实业务工具。

可以继续 QLoRA，但应由新验收集上的误差类型决定扩哪些数据；温度校准只能调整置信度，不能把错误路由变正确。是否用本地模型、Jev 或分层组合，应在这条完整链路上评估质量、覆盖率与延迟。
