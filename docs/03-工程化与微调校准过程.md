# Qwen 实验的工程化、微调与校准过程

日期：2026-09-26。本文主体详细记录第一、二轮的方案、配置、失败和边界，不能把其中 120 步、精简提示和自适应工具前向当成第四轮配置。第二轮数值见 [第二轮结果](04-第二轮结果与决策.md)。最新流程接着读 [第三轮专项](05-路由专项训练.md)、[第四轮联合训练](06-扩大数据与联合训练.md)；完整阅读顺序见 [阅读导航](00-阅读导航.md)。详细个人学习解释保存在本地 `.local/learning/`，不随仓库发布。

## 1. 研究问题与实验顺序

目标是选型中文客服决策模块，而不是证明某个模型一定更好。把三个问题分开：首 token 能否给出正确类别；工作流是否能够更少推理且保持字段一致；领域监督和概率校准是否值得本地维护。

第一轮已经完成 BF16 首 token、贪心短标签生成、Jev 对照、单次候选排列扰动、标量温度校准和工具门控。未修改权重。其结果、样本和 59 类 MASSIVE 子任务保留在 `results/baseline-v1/`，不覆盖。

第二轮顺序是：工程整理 → 固定数据和 60 类任务 → BF16 与 NF4 基线 → 有限步数 QLoRA → 开发集选检查点 → 独立校准集拟合温度 → 测试集应用 → 汇总发布检查。业务测试是第一轮看过的回归，不能称为新盲测。公开测试无法排除模型预训练接触。

## 2. 工程改造

根目录零散 Python 文件移到 `src/qwenlab/`，通过 `pyproject.toml` 安装为包，统一入口 `python -m qwenlab <command>`。配置放 `configs/`，脚本放 `scripts/`，历史报告放 `docs/archive/`，测试放 `tests/`。所有源码用项目根定位资源，不写个人盘符；从根目录运行文档命令。

本地环境和模型保留原位置，避免移动虚拟环境损坏解释器路径。密钥移入 `.local/secrets/`；日志、训练适配器和个人笔记也归到 `.local/`。`.gitignore` 排除环境、缓存、权重、原始下载、运行工作区和个人资料。

`publish.py` 不只依赖忽略规则，而是按允许列表收集源码、配置、文档、必要数据和公开结果；扫描绝对个人路径、当前密钥精确匹配、意外二进制和过大文件，发现即失败。发布 ZIP 附逐文件 SHA256。旧报告仅清理机器路径和失效链接，不改写旧结论。没有自动建远程仓库或推送。

## 3. 数据与防泄漏

MASSIVE 来源是 Amazon 官方 1.1 归档的 zh-CN 分片。按官方 partition 区分 train/dev/test。第二轮只从原始标签集合构造候选，固定 60 类；中文 test 实际支持 59 类，仍保留第 60 类作为候选，避免根据测试集删选项。

训练池为 1,715 条；开发 273 条；校准 313 条；官方 test 全部 2,974 条。划分细节、去重数量见 [数据说明](../data/README.md)。开发集用于选择检查点；校准集只拟合温度；测试不用于训练和选择检查点。

业务使用第一轮 192 条合成样本，沿用原组划分。开发集 64 条进一步按路由留出四组共 16 条验证，48 条训练；校准 56 条、回归 72 条保持隔离。业务监督未经人工复核，训练只是可行性试验。`business_split()` 按 group 分割，而不是随机把近义句拆到两边。

CrossWOZ 只使用官方 test 原始标签，确定性抽 200 个单领域用户轮次，含前 6 轮文本。输入严格不包含未来回复、状态标签和目标。它测多轮领域判断，不评贷款业务路由或完整对话任务。

`tests/test_phase2.py` 验证规范化文本不跨 MASSIVE 划分、业务组互斥、60 类候选、CrossWOZ 无状态标注进入输入、温度不改变类别。数据 SHA256 和候选规范 SHA256 同时保存。

## 4. 对 Qwen 推理做了什么

基础检查点固定为 Qwen/Qwen3-VL-2B-Instruct，由 Qwen 官方 ModelScope 下载，逐文件 revision 与 SHA256 校验。没有替换 tokenizer、词表或基础权重文件。Transformers 4.57.1、PyTorch 2.8.0+cu128、SDPA，单 GPU、单条输入。

`modeling.prompt()` 将候选映射到 A/B/C…，逐个验证它们是一个 token。MASSIVE 60 类用到大小写字母和数字。拼接系统政策、用户文本/历史/状态、候选中文解释，使用模型原生 chat template，加上 assistant 生成起始符。原始英文标签 ID 从候选文本删除，空字段也删除，但业务政策没有省略。超过 2,048 token 抛错，不静默截断。

`modeling.score()` 前向只保留最后位置的 logits，再索引候选 token。若原始词表有 V 个 token，候选 K 个，最终得到 K 维 logits，softmax 后取最大者。概率是在 K 个候选内条件归一化，不能与 Jev 内部置信度机制认定等价。第一轮另存全词表候选质量，第二轮不以此做决策。

提示还有一个值得下轮单独验证的细节：冻结版本将候选统称为“字母”，而 60 类映射包含 8 个数字符号。评分器能正确处理这些单 token，但措辞可能影响偏好。本轮没有根据测试成绩改提示；后续应在开发集比较“符号”等措辞，并另建协议版本，不能把现有结果当成 Qwen 最优提示的性能上限。

业务流程从四次独立分类改为：先 route，再 intent；只有 route=tool 才预测工具，其他路由直接写 tool=none；needs_human 由 route=human 推导。因此通常两次、需要工具时三次模型前向。原始政策仍要求工具字段服从路由。**该流程尚未完成工具可用性和所有权执行层**，本项目从未实际调用工具。

Jev 一次请求联合输出 intent/route/tool，再做同样的工具门控和人工标记推导；与本地自适应前向次数不同。对照是可用方案的端到端效果，不是架构等价证明。API 用相同业务政策、候选含义、原始输入，别名 `jev-latest` 的实际版本逐条记录。

计时：本地排除模型加载和一次预热，CUDA 同步避免异步队列造成假快；完整流程包含 tokenizer 和各任务前向。API 包含网络和解析，默认三个并发请求，请求本身延迟与总吞吐不同。没有将 API 延迟解释成纯模型速度。

## 5. 量化和训练配置

本机：RTX4060 Laptop 8GB，i9-14900HX，约 32GB 内存。基础 BF16 第一轮峰值约 4.18 GiB；第二轮训练两步验证约 3.62 GiB，只适用于当前短文本任务。

NF4 使用 bitsandbytes 0.48.1：`load_in_4bit=True`、`bnb_4bit_quant_type='nf4'`、双重量化、BF16 计算。视觉模块与 lm_head 不量化；嵌入与输出共享权重，跳过输出层很重要。NF4 主要节省权重显存，反量化和小 batch 内核开销可能让推理变慢，不能把 4bit 等同加速。

`prepare_model_for_kbit_training()` 冻结基础参数、进行训练需要的类型准备和梯度检查点设置。PEFT 0.17.1 加载 LoRA，目标严格限定语言模型 attention 的 q_proj、v_proj；断言可训练参数只能含 lora_，且不含 visual/merger。未训练视觉编码器、视觉投影、嵌入或输出头。冻结并不证明图文能力完全保持，因为图文任务也会经过已改变的语言层。

固定配置见 `configs/train-v2.json`：

|项|值|
|---|---|
|LoRA r / alpha / dropout|8 / 16 / 0.05|
|优化器|AdamW，lr=1e-4，weight_decay=0.01|
|步数|120 次优化器更新|
|micro batch / 梯度累积|1 / 8，有效每步 8 个分类问题|
|学习率|12 步 warmup，之后线性下降|
|梯度裁剪|全局范数 1.0|
|检查点|每 40 步验证一次；按开发集候选 NLL 选择|
|输入长度上限|2,048，不静默截断|
|抽样|50% 业务问题池，50% MASSIVE 池；有放回|
|候选顺序|训练每次随机置换；评测固定顺序|
|随机种子|20260926|

业务训练池的每条文本拆成 intent/route/tool 三个问题；不单独训练可推导的 needs_human。MASSIVE 只训练 intent。960 个 micro examples 是“分类问题次数”，不是 960 个独立新用户或完整 epoch。两类池平衡是为避免 1,715 条通用数据淹没 48 条业务数据；但仍只是小规模尝试，远未穷尽 Qwen 潜力。

训练目标是**候选集合交叉熵**，只监督答案位置，不生成长回答或思维链：

`loss = cross_entropy(candidate_logits[None, :], target_candidate_index)`

正式运行完成 120 步，实际可训练参数 1,605,632 个；抽样 478 个业务分类问题和 482 个 MASSIVE 问题。训练加开发验证耗时 504.48 秒，allocated 峰值 3.628 GiB；开发目标选择第 120 步。适配器权重文件 6,438,952 字节，基础模型仍需另外下载。完整训练曲线、开发记录和适配器哈希见 `results/phase2/training/`。

这与对整个词表计算答案 token 的标准 SFT 不同。模型学的是候选间区分，未强制把全部词表概率集中到候选上；因此不能用本实验断言自由生成格式改善。每个 micro loss 除以 8 再 backward；满 8 次才裁剪、step 和清空梯度。

每次验证分别平均 MASSIVE 与业务候选 NLL，再对两数据源等权平均；按这个预先固定目标选 best。测试集不参与。多任务业务验证 NLL 混合 3 种问题，不能当作单一路由准确率。适配器保存为 safetensors，adapter_config 将自动写入的本地基础模型路径替换为官方模型 ID。

训练准备会将部分非量化参数转为 float32；正式推理则按 `modeling.load_model()` 的 BF16/NF4 配置重新加载基础模型，再加载适配器。开发阶段与部署式推理的数值路径因此不是位级相同。对照测试中的未训练 NF4 与适配后 NF4 使用相同基础加载路径。固定种子、文件哈希和版本有助复现，但不保证不同 GPU、驱动与内核上逐 bit 相同。

## 6. 校准

先冻结选中的适配器，再为每个数据集/任务独立拟合一个正温度 T：`softmax(logits / T)`。在独立校准集上，对 T∈[0.05,50] 的 1,000 个对数等距值最小化 NLL。少于 10 个可校准预测时保留 T=1 并注明证据不足。

T>1 通常使分布更平；T<1 更尖。正温度不改变 logits 排序，因此分类准确率必须保持不变，只可能改善或恶化概率质量。代码验证 argmax 不变，并保留校准前结果。

工具只在模型认为 route=tool 的校准样本上有 logits，其温度是条件于这个路由筛选的估计。推导的 none/needs_human 没有模型概率，不伪造“100% 置信度”。需要端到端联合概率才能完整分析整个工具链可靠性，本轮未实现。

报告 ECE、NLL、Brier 和固定阈值覆盖率/错误数；不使用测试集寻找最好阈值。校准输出复用原推理延迟，未单独测校准运算开销，不把它写成新实测速率。生产阈值必须在足够的独立真实验证集上按漏转成本确定。

## 7. 实施中发现的问题

1. CrossWOZ 原始文件入口两次超时，改用 GitHub 官方 blob API，验证 Git blob SHA1 与 SHA256，下载成功。未用第三方不明镜像。
2. 首次 NF4 仅跳过 visual，遇到共享输出权重相关加载异常 `weight is not an nn.Module`。将 lm_head 一并排除后成功；版本未更换。失败发生在加载阶段，没有产生有效推理结果。
3. 二轮名称字典多出 `iot_hue_lightother`，导致候选为 61 类。单元测试发现后终止运行。该轮 MASSIVE 结果保存在本地 `invalid-61-candidates` 归档，不能混入正式结果；修正为原始数据的 60 类集合，重新评测。业务和 CrossWOZ 输入及候选未改变，复用其预测并附原文件哈希。两步训练冒烟也用过旧候选，仅用于验证梯度和显存，正式训练从基础模型重新开始，不加载其适配器。
4. 额外修正：数据来源清单增加 spec 哈希，防止仅记录样本哈希而漏掉候选表改变。

以上失败和重复请求也计入实验成本记录。不能只展示成功曲线、隐去配置错误或把热加载与冷启动混算。

主实验完成后，另在开发集对照“恢复候选英文 ID”和“字母改为符号”两项因素。使用同一适配器，四种组合、16 条业务 route 和 273 条公共 intent；不训练新权重、不覆盖 test。恢复 ID 只多修正一条业务开发样本，公共集下降；措辞修正只多修正两条公共开发样本。详情见结果报告，不能据此声称已经修复业务路由。

## 8. 复现与验收

完整命令见 README。核查顺序：下载清单通过校验 → 数据测试通过 → 验证候选数和划分清单 → NF4 加载 → 两步冒烟（新 run）→ 固定正式训练 → 根据开发记录选择 best → 单独校准 → 不改标签地评测 → 汇总 → 发布检查。

关键源码：`prepare_v2.py` 构造数据；`modeling.py` 共享提示和前向；`train.py` 梯度与检查点；`evaluate.py` 本地/API 对照；`calibrate_v2.py` 温度；`summarize.py` 指标；`report_v2.py` 结果导出；`publish.py` 发布检查。训练只访问 processed 数据，不导入 API 客户端，不读取密钥或 Jev 预测。

当前未实现图片处理、正式人工客服工单、线上灰度、权限执行、服务化并发/批处理和真实标注测试。这些是下一阶段，不应从本地跑通直接推导为完整生产链路。

## 9. 后续训练迭代与本文章节的对应关系

第三轮专门检验“只训练路由是否足够”：恢复原始完整提示，从基础模型重新开始，只训练四类 route，按路由宏 F1 选检查点。它使用的仍是很小的业务监督池；训练损失降低，但旧回归路由从 55.56% 降到 47.22%。完整配置、提示对照和失败归因见 [第三轮专项报告](05-路由专项训练.md)。不能把这个失败删去，也不能把第二、三轮不同提示的成绩直接相减，当作唯一的训练影响。

第四轮同时处理覆盖不足与多任务失衡：保留原始候选 ID 和完整业务政策，加入登录、记录、工具可用性、所有权等状态对照，并完整遍历公共训练池。代码入口是 `joint_data.py` 和 `joint_v4.py`，不再使用本文第 5 节的 120 步抽样训练。

第四轮的关键差异如下，精确规则与运行命令见 [联合训练方案](06-扩大数据与联合训练.md)：

|环节|第二轮|第四轮|
|---|---|---|
|公共训练记录|1,715 条候选池，有放回抽样|10,725 条去重记录，完整遍历|
|业务训练记录|48 条|2,048 条，128 表达组、20 语义家族，仍未人工复核|
|训练样本次数|960 次分类问题抽样|16,869 个任务样本；业务每条训练意图、路由、工具|
|优化器更新|120 步|2,109 步，一轮|
|批次/累积|1/8|4/2；正式推理均 batch=1|
|检查点选择|数据源等权平均 NLL|公共意图、业务意图、路由宏 F1、工具联合正确的几何平均，加退化约束|
|业务推理次数|按路由执行两或三个前向|固定三个前向，然后门控工具与推导人工标记|
|提示|精简空字段和英文候选 ID|完整政策和英文候选 ID，输出“候选符号”|
|监督目标|候选交叉熵|相同类别的候选交叉熵，显式加入任务损失权重|

第四轮训练和正式评分分离：先保存四个适配器，分别以部署精度重载来评估开发集，再按冻结规则选中第 1,582 步。训练总耗时约 2 小时 43 分钟；最后一步没有自动成为最佳模型。测试用于验证这一选择，不能据测试成绩改选最后一步或重新改标签。

## 10. 训练后的验证、速度实验和完整证据

`joint_complete.py` 在训练与主评测结束后执行旧业务和 CrossWOZ 迁移，复用固定 Jev 版本的历史公开结果，拟合独立温度并生成基础结果文档。`post_training.py` 对冻结预测作状态/语义分层；不会读取测试错例后自动更新权重。

`candidate_benchmark.py` 独立比较完整词表投影与候选行投影：理论上是对同一线性变换先选行或后选分数，但 BF16 内核可能出现数值差异。因此同时测全部开发任务的类别一致性、概率差异，以及包含分词和三任务前向的请求延迟。默认推理没有自动改动，详见 [训练后安排](08-训练后的验证与下一步.md)。

最终 [效果与速度总表](09-效果与速度验证.md) 由 `integrated_report.py` 重新读取逐条预测、核对分母并生成。它把原始准确率、工具链路、分组区间、单请求延迟、候选加速一致性和校准效果放在不同表中；同时记录标签歧义，避免把课程内高分当作泛化证明。

完整追溯链路是：**业务契约 → 数据来源和分组清单 → 冻结协议及源码哈希 → 训练日志 → 开发选择 → 校准 → 测试预测 → 速度逐条记录 → 核对后的汇总 → 发布审计**。只拿一张准确率表或一个 LoRA 文件，无法重现这个流程。
