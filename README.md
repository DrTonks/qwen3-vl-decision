# 金融客服决策模型实验

训练和实验基于Qwen3-VL-2B-Instruct候选首token方案的贷款平台智能客服的决策模型。比较本地 **Qwen3-VL-2B-Instruct 的候选首 token 分类**与 **Jev API**，用于课设“多数据源融合的贷款及风控平台”的智能客服（以中文为主）的意图识别、只读工具选择、追问、转人工和转回复模型。主实验验证文本分类；另以隔离样本库验证真实后端只读工具接入，不操作生产业务数据。实验仍在进行中。

模型可根据用户问题、认证状态和可用能力，决定**追问、检索、调用工具、回答、转人工、引导、拒绝或结束咨询**。本仓库包含数据、微调与评估代码、推理服务和实验记录；完整贷款平台在[业务项目仓库](https://github.com/0kudouchitose0/uestc_Integrated_Design)。

## 与传统客服架构的区别

传统客服架构直接把所有用户query丢给大模型，会有一些问题：

1. 成本高，因为全部请求都跑大模型

2. 不可控，大模型容易“跑偏”，遇到骚扰、无关提问会继续闲聊，需要额外做提示词工程，而且仍有可能被强行绕过

3. 动作能力弱，大模型擅长文本生成，但做确定性业务路由、分支判断不稳定，可能在该转人工的时候不转

4. 响应慢，长上下文大模型推理延迟高

考虑到以上问题，使用一个决策模型先判断用户意图和看懂用户需求，输出动作指令，能够改善会话调度和使用体验；本仓库算是针对这个决策模型的技术选型实验。

## 实验目的

其实最初考虑的是直接使用Jev来做决策（蹭TypeSafe的热度+完成课设任务）；但是考虑到我们的平台主要面向中文用户，因此需要实测Jev对中文业务和本项目规则的适配程度。而且Jev原生不支持多模态，用户可能发截图问“这个按钮怎么是灰的”、“我怎么贷不了”这样的问题；当然给Jev外挂一个OCR或者用微调的lava+图像编码器也算是一种方案，本仓库主要探索开源多模态小模型（这里使用Qwen3-VL）候选首token的方案。

思路就是给提示词约束和选项，读取模型准备输出的第一个 token 对候选符号的 logits 分布来选择答案。仍需处理完整输入，但不用逐 token 生成整段回答。最后一个输入位置的输出层可只计算候选词表行，详见[首 token 与第五轮方案](docs/10-第五轮训练与动作决策.md)。

为什么需要做决策：收到“为什么申请不了”时，客服不能立即编造原因。它可能需要追问页面位置、查询真实申请、解释已知规则，或者把争议交给人工。生成回答之前的这一步，就是本项目研究的决策。

全部交给通用大模型生成工具 JSON，可能带来多余输出、延迟和难以校准的自信；外部决策 API 则涉及网络、持续调用成本和服务依赖。所以，一个能本地部署、能接收平台截图的小模型，能否以足够低的延迟可靠决策，并在没有把握时交给其他渠道。

## 当前结论与对比

**小模型微调有效，0.8B 是当前本地研究基线；服务默认仍保留 Jev。** 新 2B 与 0.8B 均已完成 13,378 条数据的两轮训练，但尚无通过全部业务门槛的候选。

以下五种方案使用**同一份当前开发集（128 条、32 个场景组）和业务政策**。训练后选各模型完整训练实验中动作准确率最高的已评估检查点（均为第 1,673 步）；其他指标取同一检查点，不拼接单项最高值。

| 模型 | 动作准确率 ↑ | 宏平均 F1 ↑ | 工具联合准确率 ↑ | 人工召回率 ↑ | 误拒绝率 ↓ |
|---|---:|---:|---:|---:|---:|
| Jev 1.13.0 | 85.16% | 76.88% | 72.22% | 88.89% | 0.00% |
| 原始 Qwen3-VL-2B | 30.47% | 30.84% | 27.78% | 33.33% | 0.00% |
| 原始 Qwen3.5-0.8B | 37.50% | 22.37% | 44.44% | 62.96% | 13.64% |
| 训练后 Qwen3-VL-2B | 91.41% | 92.38% | 88.89% | 88.89% | 0.91% |
| 训练后 Qwen3.5-0.8B | 94.53% | 95.58% | 100.00% | 88.89% | 1.82% |

工具联合准确率以真实需要工具的样本为分母；人工召回率以应转人工的样本为分母；误拒绝率以不应拒绝的样本为分母。宏平均 F1 对八个动作等权，避免多数类掩盖少数类表现。

| 模型 | 平均耗时 | P50 | P90 | P95 | P99 | 触发工具二次判断比例 |
|---|---:|---:|---:|---:|---:|---:|
| Jev 1.13.0 | 541 ms | 324 ms | 1105 ms | 1381 ms | 1873 ms | 14.06% |
| 原始 Qwen3-VL-2B | 151 ms | 137 ms | 261 ms | 276 ms | 308 ms | 10.94% |
| 原始 Qwen3.5-0.8B | 163 ms | 176 ms | 239 ms | 265 ms | 289 ms | 63.28% |
| 训练后 Qwen3-VL-2B | 157 ms | 132 ms | 276 ms | 295 ms | 307 ms | 15.62% |
| 训练后 Qwen3.5-0.8B | 107 ms | 92 ms | 190 ms | 200 ms | 205 ms | 14.84% |

在这套合成业务开发集上，训练后 0.8B 比 Jev 多答对 12 条（+9.38 个百分点），但两者漏转人工率均为 11.11%。**这支持继续研究 0.8B，不代表通用能力超过 Jev 或已经可以替换默认服务。** 开发集参与检查点选择，最终测试与上线验证尚未完成。

Qwen 为本地 RTX 4060 Laptop 历史测量，含分词与按需工具判断；Jev 于 2026-10-16 经 7890 代理测量，含网络，按供应商返回的 `choice` 评分。均不含业务执行和回答生成，也未做同期交错计时，因此不能把耗时比解释为纯模型计算加速。Jev 成功请求 P95 为 1,381 ms；计入本次全部失败尝试与重试等待后，P50 仍为 324 ms、P95 为 1,414 ms。一条 `choice` 与概率最大项不一致，按异常记失败后总分不变，未重抽答案。

更多维度（八动作精确率/召回率/F1、分场景、权限约束）见[五模型多维性能表](docs/73-五模型多维性能对比.md)。耗时保持毫秒，P50 为中位数，P95 为 95% 样本不超过的耗时；本次 P99 只描述小样本尾部。

评测过程详见[当前五模型对比与 Jev 补测](docs/72-Jev代理补测与请求恢复.md)及[可核查结果](docs/evidence/financial-jev-current-session-v2/comparison-audit.json)。[旧 384 条协议](docs/40-Qwen3.5结果复核与Jev固定对照.md)与[旧 V5 迁移](docs/69-V5当前开发集补测与训练方案解释.md)留在实验档案，不与本表混用。

## 模型在客服链路中的位置

```text
用户输入 + 后端可信状态
        ↓
决策模型：八动作 → 若为 tool，再选择具体工具
        ↓
后端校验权限、参数、可用能力 → 工具 / 知识检索 / 人工 / 回复模块
```

本地模型读取候选首 token 的分数选动作，避免生成整段决策文本；仍需计算完整输入。候选概率不是经过验证的正确率，鉴权和执行约束仍由后端负责。`retrieve` 表示请求检索知识，**不代表知识库与检索链路已经完成**。接口以[八动作契约](configs/support-financial-v2.json)及[接入说明](docs/45-标签修订与八动作协议接入.md)为准。
